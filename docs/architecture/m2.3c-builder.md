# M2.3c Build Your Own – design

_Roles: Architect, Engineer, UX, QA. Stories: [phase-2.md](../requirements/phase-2.md) E2.8. ADRs: 010, 012. Date: 2026-10-20._

Scope: the three Build Your Own pages (requirements, workflow, test), the Planner Agent, the Foblex canvas with the node drawer, the supervisor team tiles, Monaco (static workers) and the test page with one pane per agent. Run history, sessions and downloads are in [M2.3d](m2.3d-end-user.md).

## 1. Pages (`/build`)

| Page | Route | What it does |
| --- | --- | --- |
| Library | `library` | Use cases with status, filters, duplicate, delete |
| 1. Requirements | `new` | Name, pattern, requirements text (4000 characters). *Create and plan* stores the draft and opens page 2 |
| 2. Workflow | `:id/workflow` | Planner chat (left); supervisor team tiles with drag-and-drop, or the graph canvas with the node drawer (right); *Save draft*, *Test workflow* |
| 3. Test | `:id/test` | Input form → test run; graph with the current node highlighted, timeline, one pane per step (live while an agent streams); *Publish* with description, catalog, category and note |
| Settings | `:id/edit` | Everything else: input form, output, defaults, JSON definition (Monaco), lifecycle, versions and diff, rollback |

## 2. Planner Agent

`POST /use-cases/{id}/plan` (`usecase.build`) with the builder's message, the chat history (last 12 turns used) and optionally the definition as edited so far.

- The prompt gives the model the ADR-010 node reference, the use case's requirements, input fields and output type, the **library** (published agents, tools and prompts as `name@version` with their descriptions, from `GET /use-case-assets`) and the current definition.
- The answer is one JSON object: `reply`, `definition` (complete, or `null` to just answer) and `missing` (capabilities the library lacks, with a suggested name and purpose).
- **The Planner checks its own work** with the editor's validator: structure, graph semantics (ports, cycles, variables on every path), completeness and published references. If anything fails it is told what and asked to fix it, up to 3 attempts; the final answer carries the remaining issues.
- It never creates or saves anything. The UI shows the reply, the missing capabilities (agents link to the agent editor) and an *Apply to workflow* button; *Save draft* stores what is in the editor. The model is the project's `default-chat` alias; calls go through the gateway, so cost, tokens and traces are accounted like any other (trace id `planner:<use case>`).

## 3. Canvas and drawer

The spike E0.5c editor became `GraphCanvas`. The definition is the single source of truth (`{nodes, ui.positions, limits…}`); every edit emits a new definition. Connectors are the `after` references, so the canvas, the Planner and the engine share one schema. Node settings open on double click:

| Node | Fields |
| --- | --- |
| start | display text |
| agent | agent (library picker), task, input, output variable, human in the loop |
| tool / llm | tool or prompt (picker), arguments or variables as JSON, output variable |
| router | sections (name, AND/OR, conditions field/operator/value); renaming or deleting a section rewrites the dependants |
| for_each / while | items or conditions, maximum iterations |
| end | result template |
| all but start | execute-after mode, dependencies |

Server issues (from save, or from the Planner) highlight their node and are listed in the drawer. In the test page the same component is read-only and `states` colour the nodes (running, succeeded, failed, skipped). `ui.positions` is ignored by validation, execution and the version diff.

## 4. Monaco

`MonacoEditor` (`shared/monaco-editor.ts`) loads Monaco's core editor and the JSON language on first use, with **static workers emitted by the build** (`editor.worker`, `json.worker`; no CDN, works air-gapped; the CSP already allows `worker-src 'self' blob:`). It follows the light/dark theme. It replaces the textareas of the use case definition and output schema, and the **system and user templates of Prompt Studio** (PO decision 2026-10-19). Licence: MIT; the licence gate passes.

## 5. Backend changes

Migration `0014` adds `use_case.requirements` (max 4000, copied by duplicate). Run steps now expose `agent_run_id`, which the test page uses to follow the agent over the existing SSE endpoint.

## 6. Choices to confirm with the PO

1. **Requirements attachment is not built here.** The spec has an optional file (up to 100 MB); it needs the same upload path as file inputs of runs. _Built in M2.3d ([design](m2.3d-end-user.md) §6)._
2. **The Planner proposes, the builder applies.** Nothing is applied or saved automatically; "each accepted change is a draft save" means Apply then Save draft.
3. **Chat history lives in the page**, not in the database: reloading starts a new conversation (the requirements and the saved definition stay).
4. **Planner model = the `default-chat` alias**; no separate Planner model setting yet.
5. **Live output on the test page follows the agent's token stream**; llm and tool steps show their result when they finish.
6. **The graph-editor spike page stays** (`/spikes/graph-editor`, its e2e test) until the Phase 2 exit review.
7. **Prompt Studio templates are now Monaco**: Playwright cannot `fill` them, so the e2e specs type into the editor (`fillTemplate`).
