# M1.2 LLM gateway – design

_Roles: Architect, Engineer, Security. Stories: [phase-1.md](../requirements/phase-1.md) E1.5–E1.9. ADRs: 002, 005, 006, 007, 009, 011. Date: 2026-10-17._

## 1. Module layout

All model traffic goes through `forge.gateway`; it is the only module that imports LiteLLM (import-linter, ADR-005).

| File | Owns |
| --- | --- |
| `gateway/models.py` | ORM: `model_provider`, `model`, `model_enablement`, `model_alias`, `gateway_project_config`, `llm_call` |
| `gateway/schemas.py` | Registry inputs and outputs (F1.2 fields), base-URL validation |
| `gateway/registry.py` | In-memory snapshot of providers, models, aliases and project limits; alias resolution; effective limits |
| `gateway/catalog.py` | Create, update and delete in platform or project scope; audit; publish changes |
| `gateway/adapter.py` | `ProviderAdapter` protocol and `LiteLLMAdapter`: provider mapping, error classification, secret scrubbing, Test Connection probe |
| `gateway/limits.py` | Quotas and rate limits on Valkey (reserve/reconcile), exact-match response cache |
| `gateway/pipeline.py` | `GatewayService`: chat (plain and streaming), embeddings, rerank, Test Connection, usage; writes `llm_call` |
| `gateway/seed.py` | `forge providers import-env` (lab only) |
| `gateway/service.py` | Public interface: `Gateway.build()`, `Caller`, schemas |
| `api/routes_v1.py` | OpenAI-compatible `/v1/chat/completions`, `/v1/embeddings`, `/v1/models` |
| `api/routes_models.py` | Admin Console → Model providers; Projects Studio → Models |

## 2. Data model (migration `0004_llm_gateway`)

| Table | Scope | Key columns | RLS |
| --- | --- | --- | --- |
| `model_provider` | dual | name, provider_type, base_url, secret_id → `secret`, config (api_version, region, vertex_*, headers, allow_http), status | dual policy |
| `model` | dual | provider_id, name (the value of `model` in API calls), display_name, model_type, model_id, params, context_window, max_output_tokens, embedding_dims, cost_input/cost_output per 1M tokens, capabilities[], timeout_s, max_retries, rpm_limit, all_projects, status | dual policy |
| `model_enablement` | project | model_id, project_id: which projects may use a platform model | tenant |
| `model_alias` | dual | name, model_ids[] (ordered fallback chain, 1–10) | dual policy |
| `gateway_project_config` | project | tokens_per_day, requests_per_minute, user_* variants, max_tokens_per_call, max_tokens_policy, cache_enabled, cache_ttl_s, cache_nonzero_temperature (NULL = inherit) | tenant |
| `llm_call` | project | endpoint, requested, model_id, status, http_status, error_code, attempts (jsonb), tokens_in/out, usage_source, cost, cache_hit, stream, ttft_ms, latency_ms, trace_id | tenant |

Notes:

- **Dual scope.** A platform row has `project_id IS NULL` and is written by the Super Admin through `forge_admin`; projects read it. A project row belongs to one project and is written by its Project Admin through the RLS-bound role. The tenant-isolation suite checks every new table.
- **Names.** Model names are unique per scope. A project model may not reuse a platform model name, and no model may take an alias name (`default-chat`, `fast`, `embedding`, `rerank` or a custom alias).
- **Embeddings.** Embedding models require `embedding_dims` ≤ 4000. Models with 2001–4000 dimensions are reported as `vector_storage = halfvec`, because pgvector indexes `vector` only up to 2000 dimensions (ADR-008).
- **Partitioning.** `llm_call` is not partitioned yet. Monthly partitions are planned together with `run_step` in E1.20.
- **Permission.** `llm.invoke` is added to Project Admin and Builder and to the default project token scopes.

## 3. Registry and live reload

- Every process keeps a `Snapshot` in memory: providers with decrypted keys, models, enablement, aliases and project limits.
- Loading reads every project's rows, so it runs on the reviewed `forge_admin` path (ADR-002).
- Every catalogue write publishes `pg_notify('forge_config', 'gateway')` in its own transaction. The writing process reloads at once; the others reload on the notification, through the `SettingsStore` listener (one LISTEN connection per process). After a listener reconnect everything is reloaded.
- **Resolution** of `model=<x>` for project P:
  1. P's alias `x`, otherwise the platform alias `x` → the chain filtered to models usable by P;
  2. otherwise P's model `x`, then the platform model `x`.

  The result is `404 model_not_found`, `403 model_not_enabled`, or `400 wrong_model_type` when the endpoint needs another type.
- **Usable by P.** The model and its provider are active, and either the model belongs to P or it is a platform model with `all_projects` or an enablement row for P.

**Enablement interpretation (US-1.5.3).** The Super Admin decides which projects may use a platform model (F1.2 "Enabled projects"). The Project Admin cannot widen that. Inside the project they can:

- map aliases to the models available to them;
- register project-owned providers and models, visible only in the project.

## 4. Call pipeline (ADR-005)

```text
resolve alias → capabilities (tools, json, vision) → max_tokens policy → quota reserve
→ [input guardrails, E2.11] → cache lookup → call with timeout, retries, fallback
→ [output guardrails, E2.11] → reconcile quota → llm_call row (async)
```

| Step | Rule |
| --- | --- |
| Capabilities | A request with `tools`/`tool_choice`, JSON mode or image parts skips models that do not declare the capability. If none is left: `400 capability_not_supported`. |
| Streaming | A model without the `streaming` capability still streams: the gateway makes a normal completion and sends it as one chunk. |
| `max_tokens` | Above the effective `max_tokens_per_call`: clamped (header `x-forge-max-tokens-clamped: 50->5`) or rejected with `400 max_tokens_exceeded`, per policy. When absent, it is set to the limit. The model's `max_output_tokens` also caps it. |
| Quota | Admitted while the counter is below the limit, then the counter is raised by the prompt estimate plus `max_tokens`. When the call ends, the reservation is replaced by real usage. Concurrent calls overshoot by at most one reservation (US-1.7.1 #3). Over the limit: `429` with `Retry-After` (seconds to UTC midnight for tokens, to the next minute for requests). |
| Cache | Off by default. Exact match on (project, requested name, parameters), only for `temperature = 0` unless the project allows otherwise. A hit returns `x-forge-cache: hit`, costs 0 and counts 0 tokens. |
| Retries | Timeout, connection error and 5xx are retried up to the model's `max_retries`, with full-jitter exponential backoff (0.5 s × 2ⁿ, capped at 8 s). |
| Fallback | Rate limit (429), credentials (401/403), billing (402), unknown or retired model (404/410), local rpm limit, and retries exhausted: go to the next model in the chain. |
| Final errors | 400, context window and content policy are the request's fault: no retry, no fallback. |
| Stream fallback | Possible until the first chunk. A failure after the first chunk is sent in-band as `data: {"error": …}` followed by `[DONE]`. |
| Stream usage | The chunk with `finish_reason` is held back and sent last, with the final `usage` (provider's or estimated). `stream_options.include_usage` adds the standard empty-choices usage chunk. |
| Response | One `id` per stream, `model` = the Forge model name; header `x-forge-model`. `user` is not forwarded to the provider. |

**Usage source.** For streams, LiteLLM 1.105.1 already fills missing provider usage with its own tokenizer, so the two cannot be told apart and both are recorded as `provider`. When nothing arrives at all, the gateway estimates and records `estimated` (unit-tested with a fake adapter).

**Errors on `/v1`** carry the OpenAI `error` object next to the RFC 9457 fields, so OpenAI SDKs raise the right exception class with `code` set.

| Upstream kind | HTTP | Code |
| --- | --- | --- |
| rate limit | 429 | `upstream_rate_limited` |
| timeout | 504 | `upstream_timeout` |
| connection, 5xx | 502 | `upstream_unavailable` |
| 401, 403 | 502 | `upstream_auth_failed` |
| 402 | 502 | `upstream_payment_required` |
| 404, 410 | 502 | `upstream_model_not_found` |
| context window | 400 | `context_length_exceeded` |
| other 4xx | 400 | `upstream_bad_request` |

## 5. Provider mapping

| Forge type | LiteLLM chat / embed / rerank | Notes |
| --- | --- | --- |
| vLLM | `hosted_vllm/` (all three) | |
| llama.cpp, generic OpenAI-compatible | `openai/` + `api_base`; rerank `hosted_vllm/` | Groq, Cerebras, OpenRouter, Cloudflare Workers AI and others use this type |
| NVIDIA NIM | `openai/` (default base `integrate.api.nvidia.com/v1`); rerank `nvidia_nim/` | Retriever parameters through model params, e.g. `{"extra_body": {"input_type": "query"}}` |
| Ollama | `ollama_chat/` (native `/api/chat`), embeddings `ollama/` | |
| OpenAI, Azure (`api_version`), Anthropic, Mistral, Gemini | native prefixes | |
| Bedrock | `bedrock/` | Credentials: JSON `{aws_access_key_id, aws_secret_access_key[, aws_session_token]}`; `config.region` |
| Vertex AI | `vertex_ai/` | Credentials: service-account JSON; `config.vertex_project`, `vertex_location` |

Keyless OpenAI-compatible servers get a placeholder key, because the OpenAI client refuses to start without one. Model `params` are merged under the request parameters (the request wins). They cannot override `model`, `api_key`, `api_base` or `stream`.

## 6. API surface (M1.2)

| Area | Endpoints |
| --- | --- |
| OpenAI-compatible (project API key with `llm.invoke`) | `POST /v1/chat/completions`, `POST /v1/embeddings`, `GET /v1/models` |
| Admin (Super Admin) | `/api/v1/admin/providers` (list, create, PUT, delete), `/admin/models` (list, create, PUT, delete), `POST /admin/models/test` (draft), `POST /admin/models/{id}/test`, `/admin/aliases/{name}` (list, PUT, delete) |
| Project | `/api/v1/projects/{id}/models` (list for members; write for `project.manage`), `/providers`, `/models/test`, `/models/{id}/test`, `/aliases/{name}`, `/gateway/config` (GET, PUT), `/gateway/usage` |

Credentials are write-only. On update:

- `api_key` omitted or `null` keeps the stored key;
- `""` removes it;
- a value replaces it.

Responses expose only `has_credentials`. Deleting a model used by an alias returns `409 model_in_use` with the references. Deleting a provider that still has models returns `409 provider_in_use`.

Platform limits are the runtime setting `gateway.limits` (0 = unlimited). Project values must stay within those ceilings: `422 above_platform_limit`.

## 7. Screens

- **Admin Console → Model providers.** Providers, then models filtered by LLM / Embedding / Reranker / Speech, then aliases with an ordered fallback chain. Test Connection runs on the unsaved draft. The model dialog edits per-model project enablement.
- **Projects Studio → Models.** The same component in project scope. Platform models are listed read-only and tagged *Platform*. Below it:
  - limits and cache, with the platform value as placeholder;
  - today's usage (tokens, requests this minute, calls, cost).

  Members without `project.manage` see models and aliases only.

## 9. Threat-model delta

| Threat | Control |
| --- | --- |
| Key disclosure | Envelope-encrypted secrets. Keys are never returned, logged or audited (only `credentials: set/replaced/removed`). The provider's key and key-shaped strings are scrubbed from provider error text. |
| SSRF through base URL | Only Super Admin and Project Admin configure providers. http(s) only. Link-local, multicast, unspecified and cloud metadata hosts are refused. Plain HTTP needs `config.allow_http` (on-prem endpoints). |
| Cross-project use | Platform models need enablement; project models and providers are RLS-isolated. A key's project is fixed by the key. |
| Cost or denial of service | Tokens/day and requests/minute per project and per user, per-model rpm, `max_tokens` ceiling. All are enforced before the provider is called. |
| Data to cloud providers | Per-project enablement. `user` is not forwarded. PII masking comes with guardrails (E2.11, AC7). |

The custom CA bundle from the GUI (TB3) is still open. TLS verification uses the system trust store.
