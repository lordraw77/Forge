# M3.2 Prompt and RAG evaluations – design

_Roles: Architect, Engineer, QA. Stories: [phase-3.md](../requirements/phase-3.md) E3.2. Date: 2026-10-22._

## 1. Parts
- `forge/evals/` – `evaluators.py` (pure scoring and judge prompts), `service.py` (`Evaluations`: datasets, runs, comparison), `models.py`, `schemas.py`; API `api/routes_evals.py` under `/api/v1/projects/{id}/evals` (`asset.write`); migration 0019 (`eval_dataset`, `eval_case`, `eval_run`, `eval_result`, project RLS).
- A case calls the existing `PromptStudio.test` or `RagStudio.query`, so traces, gateway calls, cost and guardrails are the usual ones; `eval_result.source_run` points to the trace. Judges call the gateway as the user.
- `rag/studio.py` now stores the retrieved chunks in rank order (`retrieval.retrieved`).
- SDK: `ForgeClient.eval_run / get_eval_run / compare_eval_runs`, `forgectl eval`. Web: Governance → Evaluations (the page replaces the single Guardrails route with tabs).

## 2. Choices (the PO may revisit)
| Topic | Choice | Why |
| --- | --- | --- |
| Execution | background task in the API process, bounded concurrency (default 2, max 8); progress in the database; a heartbeat every 30 s, a run silent for 5 minutes becomes `interrupted` | No new worker or queue; a lost pod is detected without confusing it with another pod's live run. Not durable like Temporal: an API restart loses the run (use a smaller dataset or re-run) |
| Case order and size | at most 1000 cases per dataset, executed concurrently, stored by position | Bounds cost and time |
| Pass rule | all scored evaluators pass; skipped ones ignored; at least one must score | A case with nothing to compare is not "passed" by luck |
| Thresholds | deterministic evaluators 1.0 (recall 1.0, mrr 0.5), judges 0.7, all overridable with `threshold` | Common defaults |
| Judge | one call per case and evaluator, temperature 0, JSON `{score, reason}`, text in tags marked as data | Prompt injection in judged text is the main risk; the judge is a normal gateway model, so guardrails and budgets apply |
| Faithfulness context | the 500-character excerpts of the passages cited by the answer | Full chunks are not kept in the run; long passages are judged on their start |
| Document match | by file name, case-insensitive | Expected sources are written by people |
| Comparison | matches cases by case id, else position; baseline = the older run | Editing a dataset between runs keeps matching where cases survive |
| Not included | evaluation datasets in bundles / `forgectl export`, scheduled evaluations, human labelling, answer-relevance with embeddings | Not in the stories |

## 3. Verification (2026-10-22)
Unit tests of every evaluator and the CSV/JSONL parsers; integration tests: dataset CRUD and import, a run with passing, failing, erroring and unscorable cases, a judge on the mock provider, comparison with regressions, refusals; the RAG run with recall@k, MRR, faithfulness, relevance and correctness on the full stack; `forgectl eval` gates and baselines. The web page builds and is lint-clean; it has **not** been exercised in a browser or by Playwright yet (the dev stack needs rebuilding with migration 0019).
