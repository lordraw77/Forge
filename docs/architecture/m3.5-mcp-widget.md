# M3.5 Exposed MCP server and chat widget – design

Stories: US-3.5.1–3 in [phase-3.md](../requirements/phase-3.md).

## 1. MCP server

- `forge/mcp_server/protocol.py` answers JSON-RPC itself instead of using the SDK's server classes: the SDK's `MCPServer` is built for one fixed tool list and its own sessions, while here the list depends on the project in the URL and the API key in the header. The handshake era is implemented (`initialize` echoes a supported version from 2024-11-05 to 2025-11-25; `ping`, `tools/list`, `tools/call`, `prompts/list`, `prompts/get`, notifications, batches). `server/discover` answers *method not found*, which makes current clients fall back to `initialize` (checked with the official client of `mcp` 2.3). No session id is issued, so any replica can answer; `GET` and `DELETE` answer 405.
- The exposure list is table `mcp_exposure` (migration 0023): exactly one of agent, prompt or collection per row, unique per asset and per name, removed with the asset.
- **Agent tool**: creates a conversation (`source = mcp`) as the key's owner, sends the message, polls the run up to 170 s and returns the answer with `conversation_id` in `structuredContent`; a run that ends badly is an `isError` result, not a protocol error.
- **Collection tool**: `RagStudio.collection_search`, hybrid search on the newest ready index, no reranker, top 1–10. API keys read project-wide documents only (user id `None` for the ACL lookup).
- **Prompts**: system and user templates rendered with the arguments, as one `user` message (MCP prompts have no system role).
- API for the list: `GET/POST /mcp/exposures`, `PATCH/DELETE /mcp/exposures/{id}` (`asset.write`).

## 2. Chat widget

- Tables `chat_widget` (public key `fw_…`, allowed origins, limits) and `widget_session` (SHA-256 of a random session token → conversation), migration 0023.
- Public endpoints under `/api/v1/widget/{key}`: `config`, `session`, `messages`, `runs/{id}`; and `/api/v1/widget/widget.js`. No session cookie or CSRF: the key names the widget, the `Origin` header must be on its list (403 and no CORS headers otherwise; preflight handled), requests with no `Origin` (server-side callers) pass the origin check and still meet the limits.
- A visitor's conversation runs as the Project Admin who created the widget, with `source = widget`. The answer is polled (about every 1.2 s), not streamed; failures are shown as a generic message.
- Limits in Valkey: messages per minute per visitor address (the address comes from the proxy headers when `FORGE_TRUSTED_PROXIES` is set) and per day per widget.
- Admin API `/widgets` needs `project.manage`.

## 3. Choices (the PO may revisit)

1. Hand-written protocol layer (above) rather than the SDK server; the price is that new protocol eras (the stateless 2026-07-28 envelope) need work here. Clients that only speak the new era without falling back will not connect.
2. MCP tools and prompts need the `usecase.run` scope; there is no per-exposure permission or separate "mcp" scope.
3. Agent tools wait for the answer (no progress notifications, no streaming).
4. Prompts: the latest version is served, not a tagged one.
5. Widget conversations are visible, as chats, to the user who created the widget; visitors are anonymous and unauthenticated, so the agent must not have tools that act on their behalf (nothing in Forge enforces that).
6. Widget answers are plain text (no Markdown rendering), no file upload, no citations, one theme that follows the visitor's light/dark setting.
7. The script is served by the API at `/api/v1/widget/widget.js` with a 5-minute cache; the embed code uses the origin the admin's browser is on, so behind a reverse proxy that must be the public address.
8. Exposures and widgets are not in project bundles yet.

## 4. Verification (2026-10-23)

`tests/integration/test_mcp_widget.py` (8): exposure rules and scopes; agent tool with conversation continuation; collection tool on an ingested document; prompts with missing arguments; protocol basics (versions, ping, discover refused, notifications 202, bad JSON 400, GET 405, batches); **the official MCP client** through an in-process bridge; widget conversation with origin, preflight, session isolation and disabling; widget limits (429), validation and the script. The new web page compiles and is translated; not exercised in a browser, and the script was not run in a real browser (no DOM test).
