# M3.3 Python SDK and `forgectl` – design

_Roles: Architect, Engineer, QA. Stories: [phase-3.md](../requirements/phase-3.md) E3.3. Builds on ADR-018 (bundles). Date: 2026-10-21._

## 1. Parts
- `sdk/` – the package `forge-sdk` (import `forge_sdk`, command `forgectl`), dependency `httpx` only.
  - `client.py` – `ForgeClient`: `whoami`, `export_bundle`, `import_bundle`, `list_use_cases`, `run_use_case`, `models`, `chat`; `ForgeError` carries the problem code.
  - `gitops.py` – bundle ⇄ directory, comparison.
  - `cli.py` – `whoami`, `export`, `diff`, `apply`, `run`, `chat`; settings from flags or `FORGE_URL`, `FORGE_API_KEY`, `FORGE_PROJECT`.
- Server: `ExportIn.everything` (+ `everything_versions`) exports every prompt, RAG pipeline, agent, use case and collection of the project in one call; `GET /api/v1/whoami` tells a key its project and effective permissions.

## 2. The Git format
`forge.json` (format, schema version, Forge version, source project) plus `<kind folder>/<name>.json`, one item each, keys sorted, timestamps removed. A file is the bundle item of ADR-018, so the format is the one already versioned and migrated on import; the SDK adds no format of its own. File names come from item names; names that slug alike get a numeric suffix. Re-exporting rewrites only files whose content changed and removes files of items that no longer exist (only inside the known folders, so a README or CI file next to them is safe).

## 3. diff and apply
The SDK exports the project (`latest` versions) and compares item by item, matched by kind and name (case-insensitive).
- **Compared:** the content of the *last* version of each item (templates, model, parameters, configuration, definition). **Ignored:** version numbers, notes, timestamps, tags, warnings and any field ending in `_version`, because those differ with every import and between environments.
- **Statuses:** `new`, `changed`, `unchanged`, `removed` (in the project, not in the files).
- `apply` sends only `new` and `changed` items through the existing import (policy `new_version` by default), so a change becomes one new version and a second `apply` finds nothing to do. It never deletes. Tags stay where the PO's rule of ADR-018 puts them: publishing remains an act inside Forge.
- Exit status: 0 success; `diff --exit-code` returns 1 on differences; `apply` returns 1 when an item cannot be imported; 2 for usage and API errors.

## 4. Security
- Authentication is the existing project API key; its permissions are its scopes limited to its creator's (ADR-003), so a CI key can be given `asset.write` alone. Nothing sensitive is exported (ADR-018); the key is read from the environment, never written to the files.
- `--config` (aliases, limits, groups, guardrail policy) needs `project.manage`.
- `whoami` returns the key's own project and permissions, nothing about other projects or users.

## 5. Choices to confirm with the PO
1. **Git holds the latest version only** (`--versions published|all` exist). The history lives in Forge and in Git itself; a repository with every version would grow with each edit.
2. **Match by name, update by new version**; renames in Git create new items.
3. **No deletion from Git**: removing a file does not remove the item. Deleting stays a deliberate act in the UI.
4. **No secrets, files or documents** in the repository (ADR-018).
5. **Tags are not applied by `apply`** on existing items; a promotion step (for example `forgectl publish`) is a possible next command.
6. **Name `forgectl`**, package `forge-sdk`, not published to PyPI: installed from the repository (`pip install ./sdk`) until the PO decides on a registry.
7. **Python 3.10 or newer** for the SDK (the server needs 3.12).

## 6. Not built
`forgectl publish` (move tags), streaming runs, the exposed MCP server and widget (E3.5), an OpenAPI-generated typed client, a PyPI release.
