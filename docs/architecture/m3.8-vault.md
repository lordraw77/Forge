# M3.8 External vault – design

_Roles: Architect, Engineer, Security. Stories: [phase-3.md](../requirements/phase-3.md) E3.8. Implements the `openbao` KEK source of [ADR-006](../adr/006-secrets-encryption.md). Date: 2026-10-22._

## 1. How it works
- `core/crypto.Envelope` gained **remote KEKs**: `attach(kek, make_current)`, `detach`, `use_builtin`, and an unwrap cache (2048 entries, 5 minutes). A `Sealed` value whose `kek_id` is `openbao:<key>` is wrapped by the vault (`vault:v1:…` is stored in `wrapped_dek`); the data and the AES-GCM nonce are untouched, so moving a secret between KEKs is `rewrap` (the existing `forge secrets rotate-kek` path).
- `core/vault.OpenBaoKek` speaks the Transit API (`encrypt`, `decrypt`, `keys/<name>`), with token or AppRole sign-in (relogin on expiry or a 403), a 3 s timeout and a synchronous HTTP client. `KekUnavailable` is turned into `503 vault_unavailable` by the problem handlers.
- `admin/vault.VaultLink` runs in **every process that decrypts secrets** (api, runs worker, ingest worker, the sources scheduler): it reads the `secrets.vault` setting at start, **before the gateway loads provider keys**, and again on every settings notification, so all processes follow a console change without restart.
- Console (`api/routes_vault.py`, Super Admin): `GET/PUT /api/v1/admin/vault`, `POST /test`, `POST /rewrap`. `PUT` checks the new settings with a real round trip, then stores the vault credential (JSON `{token}` or `{secret_id}`) in the secret store, sealed by the **built-in** KEK, and the rest in the setting `secrets.vault`.
- Lab: Compose profile `vault` (file storage, sealed at start), `scripts/vault-setup.sh` (init, unseal, Transit, key, policy, token), `make vault/up`, `make vault/unseal`.

## 2. Choices (the PO may revisit)
| Topic | Choice | Why |
| --- | --- | --- |
| What the vault holds | the KEK (Transit key) – it wraps data keys; Forge does not keep secrets in the vault's KV | ADR-006; no schema change; one vault round trip per distinct secret per 5 minutes |
| The vault's own credential | in the secret store under the built-in KEK, so `FORGE_MASTER_KEY` stays required | The credential cannot be unwrapped by the vault it opens; the built-in key is also the break-glass way back |
| Blocking calls | synchronous HTTP inside async code, 3 s timeout, cached for 5 minutes | `Envelope` is used synchronously in many places; an async rewrite was out of proportion. A slow vault can stall an event loop for up to the timeout, and only on a cache miss |
| Outage | reads of vault-wrapped secrets fail closed (503); no fallback to the built-in key (a secret is wrapped by one KEK) | Never decrypt by a weaker path |
| Switch-off | refused while secrets sit under the vault; the console explains the order (stop using → re-wrap → disable) | A disabled vault would leave secrets unreadable |
| Transit key rotation | transparent (ciphertext carries the version); *rewrap* in the vault (`transit/rewrap`) is not used, Forge re-wraps by unwrap + wrap | Simpler, and it also moves between KEKs |
| `derived` / convergent keys | not supported: use a plain `aes256-gcm96` key | No context is sent |
| Credential rotation | change it in the console (it replaces the stored one); AppRole secret ids can be rotated in the vault and pasted here | No automatic secret-id renewal |

## 3. Verification (2026-10-22)
Against a real OpenBao 2.4 (dev mode, in a container) and PostgreSQL: seal/open through the vault with `vault:v1:` ciphertext, transit key rotation (old data keys open, new ones are `v2`), re-wrap in both directions, AppRole with a 2-second token (relogin), a refused token, an unreachable vault (cached keys still open, a new seal and a process without the vault fail closed), and the console flow end to end: a refused setting is not saved, enabling, test, re-wrap, every secret reads back identical, switch-off refused while in use, back to built-in, disable. The lab compose profile was initialised, unsealed after a restart and removed. **Not verified:** a production-style OpenBao (HA, TLS, auto-unseal), HashiCorp Vault itself (the same API), the console page in a browser, and a worker process following a console change (the notification path is the one SMTP settings already use).
