# M3.4 Sandbox, Python tools and the `code` node – design

_Roles: Architect, Engineer, Security, QA. Stories: [phase-3.md](../requirements/phase-3.md) E3.4. Date: 2026-10-22. Follows spec-analysis T4: a separate runner with a pluggable backend._

## 1. Parts
```
api / worker-runs ──HTTP + bearer token──▶ sandbox (forge-sandbox) ──Docker Engine API──▶ throw-away container (forge-sandbox-runtime)
```
- `forge/sandbox/service.py` – `SandboxClient` (httpx), `SandboxResult`, `check_code` (parses the code without running it).
- `forge/sandbox/server.py` – the runner service. Standalone (FastAPI, httpx, standard library): it ships in `sandbox/Dockerfile` with nothing else of Forge. `POST /v1/run`, `/healthz`, `/readyz`. Settings by environment: `SANDBOX_TOKEN`, `SANDBOX_RUNTIME_IMAGE`, `SANDBOX_RUNTIME` (`runsc` = gVisor), `SANDBOX_MAX_CONCURRENCY`, `SANDBOX_MAX_MEMORY_MB`, `SANDBOX_CPUS`.
- `forge/sandbox/runner.py` – runs inside the container (`sandbox/Dockerfile.runtime`, Python slim, standard library). `scripts/sync-sandbox.sh` copies both files to `sandbox/` before a build (`make sandbox/build`).
- Tools: kind `python` (`PythonConfig`), migration 0020 (tool kind check); the call goes through `PreparedTool.execute` like any tool, so approvals, the call log and secret scrubbing are unchanged.
- Use cases: node type `code` (executable like agent/tool/llm); `ToolStudio.run_code` is what the step calls.
- Compose profile `sandbox` (`make sandbox/up`); Helm `sandbox.url` / `sandbox.token` point the chart at a runner.

## 2. How the container is built (per execution)
No network (`NetworkMode: none`), read-only root, `/tmp` tmpfs 16 MB `noexec,nosuid`, user 65534, `CapDrop ALL`, `no-new-privileges`, memory = swap limit (default 128 MB, max 512), 1 CPU, 64 pids, 256 open files, log driver capped at 1 MB. Code and arguments travel in an environment variable (at most ~90 KB of code plus arguments), which the runner removes before running the code. The result is one marker line written by the runner after the code ended, followed by `_exit`; the service reads the **last** marker line, so code that prints a fake one cannot replace it. The container is always removed; leftovers of a crashed runner are swept at start.

## 3. Choices (the PO may revisit)
| Topic | Choice | Why |
| --- | --- | --- |
| Backend | Docker Engine API (works with Docker and Podman's compatible socket). A Kubernetes backend (a Pod per run with `runtimeClassName: gvisor`) is **not built** | The pluggable seam is `Docker` in `server.py`; the Helm chart therefore cannot deploy a runner |
| gVisor | **on, tested** (2026-10-25, PO asked for it): `runsc` release-20261019.0 installed in `/usr/local/bin` on the lab host and registered in `/etc/docker/daemon.json` (`runtimes.runsc`, loaded with `systemctl reload docker`, no restart); a test runs an execution with `SANDBOX_RUNTIME=runsc` and sees the gVisor kernel. The compose default stays `SANDBOX_RUNTIME=` (runc) because a machine without runsc would fail every run: set `SANDBOX_RUNTIME=runsc` in `.env` where it is installed. SELinux is enforcing on the host and did not get in the way | gVisor is the production target; runc + the hardening is the fallback |
| Network allowlist | **built** (2026-10-25, PO): a Python tool (`allowed_hosts`) or a `code` node (`allowed_hosts`) may list hosts; they must be covered by the project's allowed hosts (Tools Studio policy), else the call is refused before it starts. The execution joins `forge-sandbox-egress`, an `internal` Docker network that has no route out, and gets `HTTP_PROXY`/`HTTPS_PROXY` with a one-run credential; the only thing on that network is the runner, whose proxy (`proxy.py`, port 8091) allows only the listed hosts, only ports 80 and 443, resolves the name itself and connects to the address it checked (refusing private, loopback and link-local addresses unless `FORGE_TOOLS_ALLOW_PRIVATE_HOSTS`), and caps connections (16) and bytes (20 MB) per run. No hosts = `NetworkMode none` as before | Code that ignores the proxy settings and opens a socket has nowhere to go; the proxy never trusts the code's idea of an address |
| Libraries | standard library only | A fixed, small image; a custom image per project is out of scope |
| Docker socket | only the runner holds it, as a non-root user in the socket's group, read-only filesystem, no capabilities | The socket is root on the host: anything that can reach the runner's API with the token can start containers of the runtime image only, with the limits above |
| Inline code in nodes | not versioned apart from the use case; the Planner Agent does not propose `code` nodes | Keeps the Planner's output to assets that need no sandbox |
| Payload size | code 40,000 chars, arguments inside ~90 KB | Environment variable limit; larger inputs belong in RAG or tools |
| Not in bundles | Python tools (like all tools today) | See M2.2 |

### 3b. Network and gVisor, added 2026-10-25
- Settings of the runner: `SANDBOX_NETWORK` (the internal network; empty = executions never get network), `SANDBOX_PROXY_HOST` (its name on that network, `sandbox`), `SANDBOX_PROXY_PORT` (8091), `SANDBOX_ALLOWED_PORTS` (80,443), `SANDBOX_RUNTIME`. Compose declares the network and attaches the runner; `/readyz` checks that the network exists and is internal.
- The proxy speaks `CONNECT` for HTTPS (the TLS session is the code's own, end to end) and absolute-URI requests for plain HTTP. HTTP clients in the standard library (`urllib`, `http.client`) honour the proxy variables by themselves.
- Not built: DNS-level filtering of anything but the proxy path; per-host rate limits; a Kubernetes backend (PO: later).
- Tests (`test_sandbox.py`, 15 pass on the real engine, 2026-10-25): an allowed host answers; HTTPS tunnels are checked like plain requests; hosts outside the list, a name that resolves to loopback and loopback itself are refused with 403; code that opens a socket directly cannot connect and an execution without hosts has only `lo`; hosts with no network configured are refused; an execution under gVisor.

## 4. Verification (2026-10-22)
Against the real container engine (runc): result and stdout, errors (division, syntax, no `run`, non-JSON result), a forged result line, timeout (container gone afterwards), memory limit, no network, read-only root / uid 65534 / no `FORGE_*` variables visible, 5 MB of output cut, token and size limits, `/readyz`. Through the API on the full stack: a Python tool created, tested, failing and timing out; a graph with `code` nodes, a router on their output, a failing node and a graph rejected for bad code. The runner image was run as a container exactly as Compose does (non-root, read-only, no capabilities, socket by group) and answered. **Not verified:** gVisor, Podman, rootless Docker, the Compose `sandbox` profile started through `make sandbox/up`, the web editor in a browser.
