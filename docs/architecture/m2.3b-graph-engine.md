# M2.3b Graph engine and supervisor – design

_Roles: Architect, Engineer, DBA, QA. Stories: [phase-2.md](../requirements/phase-2.md) E2.6, E2.7. ADRs: 004, 010. Date: 2026-10-20._

Scope: semantic validation of graph v1, the engine on Temporal, node types `agent`, `tool`, `llm`, `router`, `for_each`, `while`, `start`, `end` (and `human_approval`, which validates but stops at run time until M2.4), the supervisor pattern, run persistence, run API and a test run panel in the use case editor.

## 1. Layout

| File | Owns |
| --- | --- |
| `usecases/graph.py` | Pure: templates (`{var}`, `{var.path[0]}`), conditions, semantic validation, supervisor → graph compilation, limits |
| `usecases/engine.py` | Pure: the scheduler (`Engine`), driven by an `execute` coroutine |
| `usecases/workflow.py` | `UseCaseRunWorkflow`: runs the engine inside the Temporal workflow; each executable node is an activity |
| `usecases/activities.py` | `UseCaseRuntime` and the three activities (`uc_begin_run`, `uc_run_node`, `uc_finish_run`) on the `runs` queue |
| `usecases/runs.py` | API side: start, read, list, cancel runs |
| `api/routes_usecases.py` | `POST /use-cases/{id}/runs`, `GET /use-case-runs[/{id}]`, `POST /use-case-runs/{id}/cancel` |

`graph.py` and `engine.py` import nothing with I/O, so they run in Temporal's sandbox unchanged and are unit-tested with a fake executor (26 tests).

## 2. Semantics (ADR-010 made concrete)

- **Dependencies.** `after: ["node", "router.section", "loop.loop", "loop.done"]`; a node with a router or loop as parent must name a port. `after_mode` `all` (default) runs when every parent is resolved and at least one completed; `any` runs on the first completed parent. Fully skipped parents skip the node (dead-path elimination). Nodes that become ready together run in parallel (waves).
- **Router.** Sections in order, each with `conditions` (`field` is a variable path, `op` in `= != > < contains`, `value` literal or template) combined by `combine` (`and`/`or`). Several sections may match; `default` opens when none does. Numbers compare as numbers when both sides parse; `contains` is membership for lists and a case-insensitive substring for text. The decision is recorded in the run outputs.
- **Loops.** The body is every node below `loop` and not below `done`; a body node may depend only on body nodes, the loop and the loop's ancestors (otherwise it could wait for something unresolved: `loop_external_dependency`). Iterations are sequential. `for_each`: `{item}`, `{index}`; afterwards each output variable of the body holds the **list** of per-iteration values. `while`: condition checked before each iteration, `{index}`; variables keep their latest value. `max_iterations` (default 50, at most 200) failing the run with `max_iterations_exceeded`. Loops may nest; an inner loop's `item` shadows the outer one and the outer is restored afterwards. A text value used as `items` is read as JSON, else one item per line.
- **Variables.** The input form fields are variables; `start.output` names the whole input object. A string that is exactly one `{var}` keeps its type; other strings get text substitution (objects as JSON). Validation proves every use is defined on **all** paths (intersection at joins, also for `any`); at run time a missing value fails the step naming the variable. Values kept in the run are capped at 64 KB.
- **Steps.** A step key is the node id prefixed by its loop iterations (`each[2]/story`); it identifies the step across retries and replays.
- **Limits.** `max_steps` (default 200), `max_cost_usd` (5), `timeout_s` (1800), each taken as the smaller of the graph's and the use case defaults, checked before every step; the workflow timeout covers the whole run.
- **Supervisor.** Compiled to `start → agent_1 → … → agent_n → end`: the Team Leader gets the form values, each next agent the previous output; the result is the last agent's output. It is stored and run as a graph, so steps, limits and tracing are identical.
- **Approval.** `human_approval` nodes and `hitl: true` validate; execution stops with `approval_not_available` (tools with `requires_approval` likewise) until M2.4.

## 3. Execution and recovery

`POST …/runs` stores the run with a **snapshot of the graph it will execute** (test: the draft; published: the live version), validated inputs and merged limits, then starts the workflow `uc-run-<id>`. The workflow calls `uc_begin_run`, runs the engine, then `uc_finish_run` (status, outputs, totals; a JSON output is checked against its schema, failing with `output_invalid`).

- **Agent steps** create a detached agent run (its own hidden conversation, pinned version) and execute it with the agent runtime in the activity; the agent run id is saved on the step row **before** execution, so a retry after a worker crash continues the same run from its LangGraph checkpoint instead of starting another.
- **Completed steps are never repeated**: Temporal keeps their results in the workflow history, and `uc_run_node` returns the stored output if its row is already `succeeded`.
- **Tool steps** go through `ToolStudio` (egress policy, credentials, call log with `source = agent`); **llm steps** run a pinned prompt through `PromptStudio`.
- **Cancel** cancels the workflow; the activity heartbeats, sees the cancellation, asks the agent run to stop, and the run ends `cancelled`. Running steps are marked `failed (run_ended)`.
- Measured: a worker killed during the second of two agent steps — see the test's `USECASE_RECOVERY_S` output.

## 4. Data model (migration `0013`)

`use_case_run` (status, graph snapshot, inputs, outputs, error code/node, limits, steps, tokens, cost, trace and workflow ids, creator, times) and `use_case_run_step` (key, node, status, input, output, error, `agent_run_id`, tokens, cost, latency). Both have forced RLS. A use case with runs cannot be deleted (409 `use_case_has_runs`). Sessions arrive with M2.3d.

## 5. API rules

- `mode: "published"` (default) needs `usecase.run`, a published use case and the same visibility as the catalog (404 otherwise); `mode: "test"` runs the draft and needs `usecase.build`, and the draft must be ready (valid, complete, references published) or the answer is 422 with the issues.
- Inputs are validated against the form's JSON Schema (422 `invalid_input`).
- People with `run.read` list and read every run; others only their own (404 for the rest).

## 6. Choices to confirm with the PO

1. **Iterations run one after the other**, not in parallel (cost and rate limits stay predictable). Parallel `for_each` can be a flag later.
2. **`contains` on a list is membership, on text a substring**; nothing else (no regex).
3. **Model alias overrides in the use case defaults are stored but not applied yet** (agents keep their own models); to apply with M2.3c.
4. **Skipped nodes are listed in the run outputs, not as step rows.**
5. **A failed node fails the whole run** (no per-node "continue on error" yet).
6. **Test runs are real runs** in `use_case_run` (mode `test`), visible to people with `run.read`, and block deleting the use case.

## 7. Tests

`tests/unit/test_graph_engine.py` (26): templates, conditions, limits, validation errors, variables on all paths, loop scopes, supervisor compilation, scheduling (parallel, router, fan-out, `any`, dead paths, `for_each`, nesting, `while`, limits, approval, undefined variable). `tests/integration/test_usecase_runs.py` (9, real Temporal worker, mock model, mock HTTP API): supervisor team, published run with catalog access and pinned version, not-ready drafts, graph with loop + router + tool + prompt, failures and limits, tool error, cancel, **killed worker** (the finished step is not repeated, the same agent run resumes), project isolation.
