# M3.3 Python SDK and `forgectl` – design

_Roles: Architect, Engineer, QA. Stories: [phase-3.md](../requirements/phase-3.md) E3.3. Builds on ADR-018 (bundles). Date: 2026-10-21._

## 0. One implementation, two front ends (PO, 2026-10-22: everything `forgectl` does must be possible in the web interface)
The layout of the files, the comparison with the project and the import live **on the server** (`forge/bundles/files.py`, `Bundles.export_files / plan / sync`); `forgectl` and the web page *Projects Studio → Sync* are thin clients of the same endpoints, so they give the same files and the same answers. The SDK only moves files (zip ⇄ directory) and calls the API.

| `forgectl` | Web interface | API |
| --- | --- | --- |
| `export DIR` | Sync → *Download the project as files* (zip) | `POST /projects/{id}/export/files` |
| `diff DIR` | Sync → pick a folder or zip: the *Comparison* table | `POST /sync/read`, `POST /sync/plan` |
| `apply DIR [--dry-run] [--policy]` | Sync → *Preview* / *Apply changes*, with the conflict policy | `POST /sync/apply` |
| `whoami` | Project Info → API tokens (scopes) | `GET /api/v1/whoami` |
| API key for the CLI | Sync → *Create a key for the command line* (also Project Info) | `POST /projects/{id}/api-keys` |
| `run NAME` | Use Cases Catalog → run | `POST …/use-cases/{id}/runs` |
| `chat MODEL TEXT` | Prompt Studio / Agentic AI Studio test pages | `POST /v1/chat/completions` |
| (not in the CLI) single-bundle export / import | Export / Import page | `POST /export`, `/import` |

A picked folder keeps each file's path (the browser's relative path); the server finds `forge.json` below whatever the folder is called, ignores other files, and refuses unsafe paths (`..`, absolute). A single `.json` bundle (the format of the Export / Import page) is accepted as well.

## 1. Parts
- `sdk/` – the package `forge-sdk` (import `forge_sdk`, command `forgectl`), dependency `httpx` only.
  - `client.py` – `ForgeClient`: `whoami`, `export_files`, `read_files`, `plan`, `sync`, `export_bundle`, `import_bundle`, `list_use_cases`, `run_use_case`, `models`, `chat`; `ForgeError` carries the problem code.
  - `gitops.py` – the export zip written to a directory (only changed files; stale ones removed inside the known folders) and a directory zipped for the server.
  - `cli.py` – `whoami`, `export`, `diff`, `apply`, `run`, `chat`; settings from flags or `FORGE_URL`, `FORGE_API_KEY`, `FORGE_PROJECT`.
- Server (`forge/bundles`): `files.py` (layout, zip, comparison), `ExportIn.everything` (+ `everything_versions`), the endpoints of the table above, and `GET /api/v1/whoami` (a key's project and effective permissions).
- Web: `pages/projects/project-sync.ts`.

## 2. The Git format
`forge.json` (format, schema version, Forge version, source project) plus `<kind folder>/<name>.json`, one item each, keys sorted, timestamps removed. A file is the bundle item of ADR-018, so the format is the one already versioned and migrated on import; the SDK adds no format of its own. File names come from item names; names that slug alike get a numeric suffix. Re-exporting rewrites only files whose content changed and removes files of items that no longer exist (only inside the known folders, so a README or CI file next to them is safe).

## 3. Versions, diff and apply
(Implemented once, in `forge/bundles/files.py`.) **Versioning (PO, 2026-10-22): Git keeps the whole history.** `export` writes every version of every item (`--versions published|latest` for less), in order, in the item's `versions` list; to release a change, append a version to the file.

The SDK exports the project with all versions and compares item by item, matched by kind and name (case-insensitive), and version by version:
- **Same content = same version.** Content is everything but version numbers, notes, timestamps, tags, warnings and any field ending in `_version` (those differ with every import and between environments).
- A version of a file is *missing* when no version of the project item has its content. Missing versions are sent in order, so the project catches up with the file and nothing is sent twice.
- If the last version of the file differs from the project's last one, it is sent even when an older project version has the same content: **a revert in Git becomes a new version**, and the project's latest always ends up equal to the file's.
- A new item goes with its whole history (and its tags, which the import applies only to items it creates).
- **Statuses:** `new`, `changed` (versions to send; `diff` shows `+N version(s)`), `unchanged`, `differs` (only fields outside the versions, such as the description or a use case draft, differ: an import cannot update them, so they are reported and not sent), `removed` (in the project, not in the files). Items without versions (collections, aliases, limits, groups, guardrails) are compared whole.
- `apply` sends only `new` and `changed` items through the existing import (policy `new_version` by default) and a second `apply` finds nothing to do. It never deletes. Tags stay where ADR-018 puts them: publishing remains an act inside Forge.
- Exit status: 0 success; `diff --exit-code` returns 1 on differences; `apply` returns 1 when an item cannot be imported; 2 for usage and API errors.

## 4. Security
- Authentication is the existing project API key; its permissions are its scopes limited to its creator's (ADR-003), so a CI key can be given `asset.write` alone. Nothing sensitive is exported (ADR-018); the key is read from the environment, never written to the files.
- `--config` (aliases, limits, groups, guardrail policy) needs `project.manage`.
- `whoami` returns the key's own project and permissions, nothing about other projects or users.

## 5. Choices to confirm with the PO
1. ✅ **Decided by the PO (2026-10-22): Git holds the whole history**, and `apply` sends only the versions the project lacks (§3). `--versions published|latest` give smaller files when history is not wanted.
2. ✅ **Match by name, update by new version** (PO, 2026-10-22); a rename in Git creates a new item.
3. ✅ **No deletion from Git** (PO): removing a file does not remove the item; `diff` lists it as `removed`.
4. **No secrets, files or documents** in the repository (ADR-018).
5. **Tags are not applied by `apply`** on existing items. `forgectl publish KIND ASSET --version N [--tag staging|prod] [--remove]` moves the tags of a prompt, RAG pipeline or agent through the existing tag endpoints (`asset.write`); built 2026-10-26. Use cases are not covered (they publish through `usecase.publish`).
6. ✅ **Name `forgectl`**, package `forge-sdk`, not on PyPI (PO): installed from the repository (`pip install ./sdk`) until a registry is chosen.
7. ✅ **Python 3.10 or newer** for the SDK (PO); the server needs 3.12.
