# M3.9 Triggers of use cases – design

Stories: US-3.9.1–3 in [phase-3.md](../requirements/phase-3.md). Asynchronous runs with a completion webhook were built in M2.3d; this adds the ways a run starts without a person.

## 1. How it works

- Table `use_case_trigger` (migration 0021, row-level security by project): `kind` is `cron`, `interval` or `webhook`; `inputs` are the fixed inputs; `next_run_at`, `last_*` and `failures` track state.
- `forge/usecases/cron.py` is a small five-field cron parser (`*`, lists, ranges, steps, Sunday 0 or 7, either day field when both are restricted, IANA time zones). There is no new dependency.
- `forge/usecases/triggers.py`: `Triggers` does CRUD and firing. It calls `UseCaseRuns.start` as `Actor(created_by)` in `published` mode with `can_build=True`, so a trigger goes through the same input validation, catalog rules, egress check of the webhook and audit as a manual run.
- Scheduler: a loop in every API process (every 20 s). `fire_due` selects due rows `FOR UPDATE SKIP LOCKED`, moves `next_run_at` to the next slot *after now* in the same transaction, and then starts the runs; replicas therefore never fire a slot twice and downtime produces one run, not a backlog.
- Inbound URL: only the SHA-256 of the token is stored (prefix `ft_`); the endpoint looks it up as `forge_admin` and refuses unknown, paused or non-webhook triggers with 404.
- API: `GET /projects/{p}/triggers`, `POST /projects/{p}/use-cases/{id}/triggers`, `PATCH|DELETE /triggers/{id}`, `POST /triggers/{id}/rotate-token`, `POST /triggers/{id}/fire`, public `POST /api/v1/triggers/{token}`. Permission `usecase.build`.
- Web: `/build/:id/triggers` (link *Triggers* in the library).

## 2. Choices (the PO may revisit)

1. A trigger runs as its creator. *(Changed 2026-10-25, PO)*: at every firing the creator is checked (active user, still a member with `usecase.build`, or Super Admin). A schedule whose creator fails the check is switched off at once (`last_error` says why); an inbound URL answers 409 `trigger_owner_lost_access`. A Builder who switches the trigger on again takes it over (it then runs as them).
2. Only published use cases run; a trigger on a use case that is not (or no longer) published records `failed` and counts toward the five-failure pause.
3. Inputs are fixed JSON; file inputs are not supported by triggers.
4. Cron and interval slots are skipped, not queued, when the previous run is still going: overlapping runs are allowed.
5. Webhook triggers are never paused by failures (a caller sees the error directly). *(Changed 2026-10-25, PO)*: each token is limited to 30 calls per minute (Valkey counter; 429 `rate_limited`), constant `WEBHOOK_PER_MINUTE`, not yet a per-trigger setting.
6. Queue consumers (Kafka, SQS, NATS) are not built; an inbound URL is the integration point for now.
7. Daylight-saving gaps and repeats are handled by plain wall-clock arithmetic in the trigger's time zone and were not tested.

## 3. Verification (2026-10-23)

`tests/unit/test_cron.py` (13 cases) and `tests/integration/test_triggers.py` (5: interval fire and move on, validation, token run and rotation without a session, permissions and *Run now*, pause after five failures and reset) pass on the lab stack. The web page compiles and every message has an Italian translation; it was not exercised in a browser and has no Playwright spec yet.
