# M2.3a Catalogs and use case model – design

_Roles: Architect, Engineer, DBA, Security, QA. Stories: [phase-2.md](../requirements/phase-2.md) E2.4, E2.5. ADRs: 001, 003, 010, 011, 018. Date: 2026-10-20._

Scope of this step of M2.3: catalogs and categories, access by Role Name, the use case library with versions, lifecycle and rollback, an end-user catalog view, and use cases in bundles. The graph engine, supervisor, the builder (Planner, canvas) and runs follow in M2.3b to M2.3d.

## 1. Module layout

`forge.usecases` is a new domain module. It reads agents, tools and prompts only through their service interfaces (import contracts enforce this); it registers reference checks with the three studios so that deleting a pinned asset is refused.

| File | Owns |
| --- | --- |
| `usecases/models.py` | ORM: `catalog`, `category`, `catalog_access`, `category_exclusion`, `use_case`, `use_case_version` |
| `usecases/definition.py` | Reference extraction (`agent_ref`, `tool_ref`, `prompt_ref` as `name@version`), structural validation, readiness checks, input form → JSON Schema |
| `usecases/schemas.py` | Inputs and outputs; the input form fields; defaults |
| `usecases/service.py` | `UseCaseStudio` |
| `api/routes_usecases.py` | REST under `/projects/{id}` |

## 2. Data model (migration `0012_usecases`)

All tables have `project_id` and forced RLS.

- `use_case` holds the **working draft** (settings, input form, output, defaults, definition) plus `latest_version`, `published_version`, `status` and `dirty` (draft differs from the published version).
- `use_case_version` is insert-only: a publish snapshots the draft with its generated input JSON Schema. Rollback moves `published_version` to an older row and restores the draft from it; no row is rewritten.
- Access is two small tables: `catalog_access (role_name, catalog)` and `category_exclusion (role_name, category)`. Enabling a catalog grants all its categories; exclusions switch single categories off, including categories created later (they are visible by default).

## 3. Rules

- **Lifecycle.** `draft → testing → published → deprecated`. Testing and publishing need a valid, complete definition (supervisor: at least one agent; graph: start node and at least one agent/tool/llm node) and references that are published: agents and prompts tagged `prod`, tools with a published version; a pinned version above the published one is refused. Publishing also needs a catalog (active) and a category. Editing a published use case only changes the draft; new runs keep using `published_version` until the next publish.
- **Rollback** re-checks references, so a version that points at something no longer published cannot go live.
- **Delete.** Blocked while a catalog/category files it (409 on the catalog side), while other modules refer to it, and (from M2.3b) while it has runs. Deleting an **agent, tool or prompt** that a use case's draft or live version pins is refused with the use case names (new `agent_in_use`).
- **Catalog view.** `GET /catalog/use-cases` lists published use cases in active catalogs; people with `usecase.build` see all, others only the categories their Role Name was granted (API keys use the Role Name of the key's creator). A use case the caller may not see answers 404. The response carries the input form and version, never the definition.
- **Names.** Catalog and category names are unique per project (case-insensitive); use case names allow parentheses so `"(imported)"` copies fit.

## 4. Bundles

Kind `use_case` joins ADR-018 (additive, `schema_version` stays 1): settings, input form, output, defaults, definition, catalog and category **by name**, and the chosen published versions as `history`. Exporting with dependencies adds the agents the definition refers to. Import creates or updates the **draft** and never recreates published versions (publishing stays deliberate); references are re-pinned to the published version of the same name in the target project, and unresolved names are reported as warnings. Policies `new_version` (updates the draft), `rename`, `skip` apply as for the other kinds.

## 5. Choices to confirm with the PO

1. **No catalog is visible to a Role Name until the Project Admin enables it.** A fresh project shows End Users an empty catalog page. Alternative: enable the three built-in catalogs for the default "User" and "Operator" roles at project creation.
2. **Builders see every published use case in the catalog view**, not only what their Role Name was granted, so they can try what they publish. Admins and Builders cannot preview a restricted End User's view.
3. **Bundles import the draft only**, not the published history.
4. **Built-in catalogs are created lazily** on first access (idempotent), so projects created before this migration get them too; they can be disabled, not renamed or deleted.
5. **Definition editing is JSON in a text area** in this step (Monaco comes with the builder in M2.3c).
6. **A draft may be saved with an invalid workflow reference only when the structure is sound**: syntax and structure errors are refused on save (422), unpublished or missing references are accepted in a draft and refused at testing/publish.

## 6. Tests

`tests/unit/test_usecases.py` (12): input schema, field validation, body consistency, reference extraction, structural and completeness checks. `tests/integration/test_usecases.py` (8): built-in catalogs and their protection, catalog/category management and delete blocks, library validation and filters, publish gates, immutable versions with diff, rollback and deprecate, access by Role Name (including 404 for hidden use cases and the Viewer role), bundle round trip, cross-project isolation. The tenant isolation suite covers the new tables automatically.
