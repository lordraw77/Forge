## 2. Load test results (2026-10-22)
Host: 4 vCPU, 7.5 GB, **shared with another project and swapping** (so numbers are pessimistic and for comparing builds, not for sizing). One API process, one runs worker, one ingest worker as host processes, PostgreSQL, Valkey, OpenSearch, SeaweedFS and Temporal in Docker on the same host, the mock model provider (answers in ~1 ms), SQLAlchemy pools of 5. Run: `scripts/loadtest-env.sh`.

| Target (LLM time excluded) | Measured | Verdict |
| --- | --- | --- |
| Gateway overhead < 50 ms p95 | direct provider p95 1.8 ms; through the gateway p95 33.6 ms → **overhead p95 31.8 ms** (p50 21.7 ms), 300 sequential calls over HTTP. At 16 concurrent callers the one API process serves ~50 calls/s (p50 306 ms, p95 407 ms: queueing, CPU-bound at ≈20 ms of server time per call) | **met** (per call); throughput of one process is ~50 calls/s |
| Hybrid retrieval < 300 ms p95 | **p95 27 ms** one query at a time on a **800-chunk** corpus (embedding, vector + BM25, fusion; p50 17 ms); with 16 concurrent queries p95 351 ms | met on 800 chunks. **The target is for 1M chunks and that was not re-measured here**; the Phase 0 spike measured 159 ms p95 at 1M rows (pgvector HNSW + OpenSearch) and the shipped schema was not run at that size |
| 200 concurrent agent runs per worker node | **200 started in 9.7 s, all 200 succeeded, last one finished after 51 s** with one runs worker (`FORGE_WORKER_RUNS_ACTIVITIES=200`), mock model, no tools | met for a trivial agent; real runs also wait for models and tools |
| Ingestion ≥ 50 pages/s per worker (text) *(2026-10-25: for 1-page documents the knowledge-base build went from 9.6 to 18.5 pages/s after batching, see §5)* | **100 pages/s** for 10-page documents (40 docs, knowledge-base build, one ingest worker, 16 activities). For **1-page documents 9.6 pages/s** (400 docs): a fixed cost of about 100 ms per document (Temporal round trips, database) dominates | met for documents of realistic size, **not met for one-page documents** |

### What the load tests found and what changed because of it
1. **Agent runs were capped at 8 concurrent activities per worker** (hard-coded): 200 concurrent runs could not have been served. Now `FORGE_WORKER_RUNS_ACTIVITIES` (default 64) and `FORGE_WORKER_INGEST_ACTIVITIES` (default 8).
2. **PostgreSQL's default of 100 connections ran out** (three Forge processes keep up to ~30 each, Temporal ~30), turning polls into 500s under load. Compose and the chart now start PostgreSQL with `max_connections=300`; `FORGE_DB_POOL_SIZE` sizes a process's pool. *The running dev database keeps 100 until its container is recreated.*
3. **Knowledge-base builds were ~4 documents/s**: lock-step batches of 4 documents, each document forcing an index refresh and a one-by-one `finish_document` call. Now a sliding window of 16, no forced refresh per document in a build (one refresh at the end, before the base turns ready), concurrent `finish_document`: a 400-document build went from 104 s to 42 s, 10-page documents reach 100 pages/s.
4. **Uploads were sequential per file** (S3, three transactions, workflow start each): now eight files at a time per request (same-path files keep their order): 400 files from 30 s to 16 s.
5. A latent defect surfaced by the reindex test: the OpenSearch role lacked the scroll permission delete-by-query needs, so deleting a document or collection failed with 403 (fixed in the role files; see the changelog for existing deployments).

### Not measured
1M chunks; more than one API or worker process (the targets say "per worker node": add processes and rerun); real model latency; the Helm chart under load; sustained runs (minutes, not hours); memory growth.

## 3. Disaster recovery drill (2026-10-22, `make pitr/drill`)
See the table in the [runbook](../operations/dr-runbook.md#drill-results): archive lag 54.6 s (target 900 s), recovery 5.0 s for a 101 MB database (target 3,600 s), data exactly as at the chosen moment. Backups were checked to be encrypted (the stored objects carry no LZ4 or tar magic). The `backup` sidecar loop was run on its own and took and pruned a base backup; the Compose overlay and `pitr/restore` wrapper were validated with `docker compose config` but **not run against the live stack** (that would recreate the development database).

## 4. Choices (the PO may revisit)
| Topic | Choice | Why |
| --- | --- | --- |
| Tool | WAL-G (Apache-2.0) | Works against any S3 over plain HTTP (SeaweedFS), libsodium encryption, single binary; pgBackRest needs TLS to the repository |
| Backup scope | the whole PostgreSQL instance (Forge, Temporal) at one moment | One consistent point; Valkey is disposable, OpenSearch is rebuilt, documents are S3's job |
| Retention | 7 daily base backups and their WAL | Reviewable in one value; covers a week of mistakes |
| RPO | 60 s `archive_timeout` | Measured lag 55 s; a synchronous standby would be needed for zero |
| Restore into a new volume only | the Compose wrapper keeps the old data in a named volume | A restore must never destroy the only copy |
| Load tests | a script that runs against any deployment, plus a lab harness | The same numbers can be taken on the customer's hardware |


## 5. One-page documents (2026-10-25)
PO asked to improve ingestion of small documents. Changes in `rag/ingest.py`: a knowledge-base build hands documents to the worker in **batches of 8** (`rag.index_batch`: four documents at a time inside one activity, each settled with `finish_document`; four batches in parallel), instead of two Temporal activities per document; the single-document workflow ends with **one** `rag.finish_ingest` activity instead of `finish_document` plus one `finish_kb` per knowledge base. Both are behind `workflow.patched`, so workflows already running keep their old path.

Measured on the same shared 4-vCPU host (`scripts/loadtest-env.sh --scenarios ingest --docs 400 --pages-per-doc 1`): knowledge-base build **21.6 s for 400 documents = 18.5 pages/s** (before: 9.6). The upload path (sequential uploads in the load script) takes 33.9 s end to end (11.8 pages/s). The 50 pages/s target is **still not met for one-page documents on this host**. What is left per document is one embedding call through the gateway, five database sessions and one search bulk request; the next lever is embedding and indexing a whole batch in one go (one `embeddings` request per 32 chunks across documents, one bulk request per batch). Not done: it changes `index_document` deeply and the host is too loaded to tell whether the gain would show.
