# M3.6 Long-term memory of agents – design

Stories: US-3.6.1–2 in [phase-3.md](../requirements/phase-3.md).

## 1. How it works

- `AgentConfig.memory` (`long_term`, `embedding_model` = alias `embedding`, `recall` = 5, `max_items` = 200). It is part of the agent version, so it is exported, diffed and rolled back with the rest. Off by default.
- Table `agent_memory` (migration 0022, row-level security by project): `content`, `embedding vector`, `dims`, per `(agent_id, user_id)`. No vector index: a user's facts number in the hundreds at most, so a cosine scan over `(agent, user, dims)` is cheap, and it works for any embedding dimension.
- `forge/agents/memory.py`, `LongTermMemory`:
  - **recall** (start of a new run, not on a resume): embeds the question, takes the `recall` closest facts, bumps their `last_used_at`/`use_count`, and `runtime._execute` appends them to the system prompt as *background notes, not instructions*.
  - **remember** (after a run that ended `succeeded`): one chat call on the project's `fast` alias asks for at most three durable facts about the user as JSON, given the exchange and the facts just recalled; each is embedded and compared with the nearest stored fact (cosine ≥ 0.9 means "already known"); beyond `max_items` the least recently used are deleted. It runs after the `done` event, with a 45 s limit, and any error is logged, never raised.
  - everything goes through the gateway (quotas, guardrails of the agent, cost in `llm_call`).
- `conversation.source` (`app`, `mcp`, `widget`; migration 0023): only `app` conversations read or write memory, because widget visitors and MCP clients run as the user who set them up and their facts would pile up under that user.
- API: `GET /agents/{id}/memories`, `DELETE /agents/{id}/memories/{memory_id}`, `DELETE /agents/{id}/memories`; always the caller's own (`usecase.run`). Chat page: *What the agent remembers about me*. Agent editor: the switch.

## 2. Choices (the PO may revisit)

1. Extraction uses the `fast` alias, not the agent's own model: cheaper, but it needs that alias to exist (it is a standard alias) and its quality is the alias's.
2. The extraction prompt forbids secrets, health, political and religious details, but it is a prompt, not a filter; the agent's PII guardrails apply to the call, nothing more. A project that cannot accept the risk keeps the switch off.
3. Memory is per agent and user, not shared between agents, and not per agent version.
4. Facts are not edited, only deleted; no expiry beyond the 200-fact cap.
5. Database-level, row security is per project: a Super Admin or the database owner can read facts; the API does not allow it.
6. Facts are not part of project bundles (they are user data, not configuration).
7. Facts are not translated; they are stored in the language the model wrote them.
