# M1.5 Single agent and tracing – design

_Roles: Architect, Engineer, DBA, Security, QA. Stories: [phase-1.md](../requirements/phase-1.md) E1.18–E1.21. ADRs: 002, 004, 005, 009, 011, 018. Date: 2026-10-19._

## 1. Module layout

`forge.agents` owns agents, conversations, runs and the tool registry. Models are called only through `forge.gateway.service`; prompts come from `forge.prompts.service`; retrieval comes from `forge.rag.service`. LangGraph and psycopg are imported only by `agents/runtime.py` and the activity (ADR-004, rule 5).

| File | Owns |
| --- | --- |
| `agents/models.py` | ORM: `agent`, `agent_version`, `agent_tag`, `conversation`, `agent_run`, `run_step`, `tool_call_log`, `run_feedback` |
| `agents/schemas.py` | Agent configuration, runs, steps, events, feedback |
| `agents/studio.py` | `AgentStudio`: library, versions, tags, reference checks, conversations, run views, feedback, usage totals |
| `agents/tools.py` | Tool registry: `rag:<pipeline>` retriever tools, `http_get`, `current_time`; JSON schemas; idempotent execution |
| `core/egress.py` (moved from agents in M2.2, shared with Tools) | Outbound HTTP guard: allowlist per agent, private ranges refused, redirects re-checked, size and time caps |
| `agents/runtime.py` | LangGraph ReAct graph, gateway chat adapter, limits, event publishing, checkpoint pool |
| `agents/workflow.py` | Temporal `AgentRunWorkflow` and activity `run_agent` |
| `agents/events.py` | Run events on Redis streams (publish, replay, follow) |
| `observability/telemetry.py` | OpenTelemetry setup, Temporal interceptor, trace ids in logs |
| `observability/metrics.py` | Prometheus registry and the internal `/metrics` server |
| `api/routes_agents.py` | `/api/v1/projects/{id}/agents/...`, conversations, runs, SSE |
| `guardrails/injection/` | Dataset, generator, detectors and runner of E1.21 (`forge injection run`) |
| `bundles/service.py` | Agents export and import with the other assets (ADR-018) |

## 2. Data model (migration `0009_agents`)

All tables have forced RLS (ADR-002). The generic isolation suite covers them.

| Table | Notes |
| --- | --- |
| `agent` | name (unique per project), description, latest_version |
| `agent_version` | **Insert-only.** `config` (validated JSON, below), `prompt_id` + `prompt_version` (pinned), `model` (alias or model name), note |
| `agent_tag` | `draft`, `staging`, `prod` → version, as prompts and pipelines |
| `conversation` | project, agent, version used, title, user; a chat thread. Each user message is one run |
| `agent_run` | conversation, agent, version, input, output, citations, status (`queued`, `running`, `succeeded`, `failed`, `cancelled`), failure reason, limits snapshot, totals (tokens in/out, cost, latency, steps), `trace_id`, Temporal workflow id, user. Updates allowed only on the run's own lifecycle fields |
| `run_step` | ordinal, kind (`llm`, `tool`), name, status, input, output, tokens, cost, latency, TTFT, model used, `llm_call_id`, `tool_call_id`, `span_id` |
| `tool_call_log` | Idempotency (ADR-004 rule 2): key `{thread_id}:{tool_call_id}` unique; stores the tool result and is returned on a repeat |
| `run_feedback` | one per (run, user): rating `up`/`down`, comment |

**Agent configuration** (`agent_version.config`):

| Field | Meaning |
| --- | --- |
| `prompt` | `{prompt_id, version}`. The prompt's **system template** (rendered with `prompt_variables`) and few-shot examples form the agent's instructions. Its user template is not used: the chat message is the user turn |
| `model` | Alias or model name, resolved on **every** call. Changing the alias target changes the provider with no change to the agent (AC1) |
| `tools` | List of `{kind: "rag", pipeline_id, version, name?, description?}` or `{kind: "builtin", name: "http_get" \| "current_time", config}` |
| `limits` | `max_steps` (default 8; it counts **model calls**, the agent's reasoning steps, not tool calls), `max_tokens` (total, default 50,000), `timeout_s` (default 120), `max_cost_usd` (default 1.00). Hard ceilings are set by the platform (25 / 500,000 / 900 s / 50 USD) |
| `temperature`, `max_output_tokens` | Passed to the model |

References are pinned to versions at save time: the pipeline reference carries its version (or follows the `prod` tag when `version` is empty, resolved when the agent version is saved and stored as a number). A prompt or a pipeline referenced by an agent cannot be deleted (US-1.11.2 #3, now also tested with agents); the reference check lists the agents.

## 3. Runtime (ADR-004)

```text
API: POST …/conversations/{id}/messages
  → insert agent_run(queued), start Temporal workflow AgentRunWorkflow(run_id)  [queue "runs"]
  → return run_id; the client opens GET …/runs/{id}/events (SSE)

AgentRunWorkflow                         activity run_agent(run_id, attempt)
  start_to_close = timeout_s + 30           LangGraph ReAct graph, thread_id = "run:{run_id}"
  heartbeat 60 s, retries with backoff      AsyncPostgresSaver checkpoints (schema langgraph)
  non-retryable: validation, budget,        LLM calls: gateway chat, tools=[…]
  cancelled                                 tools: tool_call_log idempotency
  signal cancel_run                         events: Redis stream run:{run_id}
```

- **Graph.** Two nodes, `model` and `tools`, as in the spike. `model` calls the gateway with the conversation messages and the tool schemas; if the answer has tool calls the graph goes to `tools`, which executes them (concurrently when independent) and returns to `model`; otherwise it ends. LangGraph's prebuilt agent is not used, so limits, cost and events are in our code.
- **Limits** are checked before each model call and after each step: steps, tokens (in+out), cost, wall time. Exceeding any ends the run `failed` with `limit_exceeded:<which>` (US-1.18.1 #2). The last assistant text, if any, is kept as output.
- **Resume** (AC6, agent level). The activity chooses the start from the checkpoint (`aget_state`): no state → initial input; pending nodes → continue; finished → return the stored answer. A re-executed `tools` node returns stored results from `tool_call_log`, so side effects do not repeat. `run_step` rows are keyed by (run, ordinal) and upserted, so a retry does not duplicate them.
- **Cancel.** The stop button calls `POST …/runs/{id}/cancel`: the API sets `cancel_requested` on the run and signals the workflow; the activity polls the flag between steps and on each heartbeat, ends the run `cancelled`, and publishes the final event. A run stuck in `queued` is cancelled directly by the API.
- **Streaming.** The model call uses the gateway's stream; token deltas go to the Redis stream as `token` events. Step events (`step_started`, `step_finished` with tool name, arguments, result summary, citations) and the final `done` event are also persisted in `run_step`/`agent_run`, so a late or reconnecting client replays from the database when the Redis stream has expired (stream TTL 1 h after the run ends).
- **Worker.** `worker runs` now needs the database, Redis, the gateway and the retriever (OpenSearch client). It does not need Docling or object storage, so it stays on the small image.
- **Conversation memory.** The model sees the conversation's earlier user and assistant messages (final answers only, not tool traces), trimmed to the model's context window by the exact tokenizer when one is set.

## 4. Tools

- **RAG retriever tool.** One per configured pipeline: name `search_<pipeline>`, parameter `query`. It runs the pipeline's pinned version retrieval (no synthesis, the agent writes the answer) with the **caller's** groups and roles, so document ACLs apply to agent runs as to RAG Studio (AC4). It returns numbered passages `[n]` (numbering continues across calls in one run) with document and page, and records the citations. The final answer's `[n]` markers resolve to the recorded citations, which the chat shows as links.
- **`http_get`.** Parameters `url`. Allowed only for hosts in the agent's `allowed_hosts` (exact or `*.suffix`); an empty list disables the tool. Plus platform rules, applied after DNS resolution and on every redirect: only `http`/`https`, no private, loopback, link-local or metadata addresses (SSRF), at most 3 redirects, 10 s, 256 KB read, text-like content types only, the body is returned as a quoted data block, never as instructions. `FORGE_AGENT_ALLOW_PRIVATE_HOSTS` is a deployment flag for lab use (off by default), because the lab hosts are on a private network; it is not editable from the GUI.
- **`current_time`.** Returns the date and time in a given IANA zone. No network; gives demos and tests a deterministic tool without side effects.
- Tool results are truncated to 8,000 characters for the model and kept in full (up to 64 KB) in `run_step`.
- Tools that need approval (HITL) and tool authoring arrive in Phase 2 (Tools Studio, E2.x); the tool interface already carries `requires_approval` so the registry does not change.

## 5. Accounting and tracing (E1.20)

- **Per LLM step:** the gateway records `llm_call` with `trace_id = "run:<run_id>"`. The step stores the `llm_call_id`, model used, tokens, cost, latency and TTFT from the gateway's `CallInfo` (streaming calls report the same numbers at the end).
- **Reconciliation (AC9).** Run totals are the sums of its steps, written in the same transaction as the last step. `GET …/usage` returns project daily totals computed from `agent_run`; the test checks `agent_run` totals = Σ `run_step` = Σ `llm_call` with the run's trace id, and daily totals = Σ runs.
- **Run view.** Steps in order with input, output, tokens, cost, latency, TTFT, outcome; totals; citations; feedback. Visible to roles with `run.read`; `run.read.own` sees only the user's own runs (US-1.20.1 #3), enforced in the query, not in the UI.
- **OpenTelemetry.** SDK in API and workers; FastAPI, httpx and Redis instrumentation (the SQLAlchemy instrumentation supports SQLAlchemy < 2.1 only and Forge runs 2.1, so there are no SQL spans yet); the Temporal tracing interceptor links API → workflow → activity; each graph step and gateway call is a span with GenAI semantic attributes (`gen_ai.request.model`, `gen_ai.usage.*`). Prompt and completion text is **not** put in spans by default (ADR-009). Export is OTLP to the collector when `OTEL_EXPORTER_OTLP_ENDPOINT` is set; otherwise tracing still produces ids for logs and the run view with no exporter.
- **Logs.** The JSON logger adds `trace_id`, `span_id`, `run_id`, `project_id` from context variables.
- **Prometheus.** `FORGE_METRICS_PORT` (default 9100) starts an internal HTTP server on each process (`api`, `worker runs`, `worker ingest`), not on the public API port and not routed through nginx. Metrics: `forge_http_requests_total` and duration by route, `forge_gateway_calls_total`, `forge_gateway_tokens_total`, `forge_gateway_cost_usd_total`, `forge_agent_runs_total{status}`, `forge_agent_run_duration_seconds`, `forge_agent_steps_total{kind}`, `forge_tool_calls_total{tool,status}`, `forge_worker_activities_inflight`. The Compose `observability` profile scrapes them.
- **Langfuse (PO decision 2026-10-19, option C).** Forge does not depend on Langfuse. A Compose profile `langfuse` (Langfuse, ClickHouse, with the existing PostgreSQL, Valkey and SeaweedFS) is off by default, and the collector gets an optional OTLP exporter to it. ADR-009 is amended. The profile is documented and its configuration validated; a full Langfuse installation in the lab is not an exit criterion.

## 6. API surface (ADR-011)

Under `/api/v1/projects/{project_id}`:

| Method and path | Permission | Purpose |
| --- | --- | --- |
| `GET/POST /agents`, `GET/PATCH/DELETE /agents/{id}`, `POST /agents/{id}/duplicate` | `asset.write` | Library and CRUD with the usual cursor, status and time filters |
| `GET/POST /agents/{id}/versions`, `GET /agents/{id}/versions/{n}`, `POST /agents/{id}/publish`, `PUT/DELETE /agents/{id}/tags/{tag}` | `asset.write` | Versions and tags |
| `GET /agents/available` | `usecase.run` | Published agents a chat user can pick (name, description) |
| `POST /conversations` (agent, optional tag/version), `GET /conversations`, `GET /conversations/{id}` | `usecase.run` | Chat threads; each user sees their own |
| `POST /conversations/{id}/messages` | `usecase.run` | Add a user message; starts a run; returns `run_id` |
| `GET /runs/{id}`, `GET /runs` (filters: agent, status, user, time) | `run.read` or `run.read.own` | Run view and list |
| `GET /runs/{id}/events` | same | SSE: replay then follow |
| `POST /runs/{id}/cancel` | `usecase.run` (own) or `run.read` holders with `asset.write` | Stop |
| `PUT /runs/{id}/feedback` | `usecase.run` (own run) | Thumbs and comment |
| `GET /usage` | `run.read` | Daily totals from runs |

Errors: `agent_not_published` (409 when chatting with a draft-only agent as a non-builder), `agent_in_use` (409 with references), `limit_exceeded` appears as the run's failure reason, `tool_not_allowed`, `run_not_found`.

The SSE event types are `run_started`, `token`, `step_started`, `step_finished`, `citations`, `done`, `error`; each carries `run_id` and a monotonic `seq`; `Last-Event-ID` resumes after `seq`.

## 8. E1.21 Injection test set

Code and data live in `backend/src/forge/guardrails/injection/` so the runner ships in the image.

- **Data** (`data/v1/`, versioned): `attacks.jsonl` (440) and `benign.jsonl` (440), 220 English and 220 Italian each, records `{id, lang, category, text}`, plus `manifest.json` with the version, seed, counts per language and category, and the SHA-256 of every file (the runner refuses a file that does not match).
  - Attack categories: direct override, role-play and persona, system-prompt extraction, encoding and obfuscation (base64, rot13, leetspeak, spaced letters, invisible characters, look-alike letters), delimiter and format breaking, indirect injection (in documents, mail, web results, READMEs), multi-turn set-ups, tool misuse and exfiltration (metadata endpoints, localhost, `file://`, send-to-attacker).
  - Benign categories include look-alikes so that false positives are measurable: security discussion and quoted attack phrases, ordinary uses of "ignore", "previous instructions", "system prompt", "override" and "root", legitimate role-play, business documents with imperative text, prompt-writing questions, legitimate tool use.
- **Generation.** `python -m forge.guardrails.injection.generate` builds the main set from reviewed fragments with a fixed seed (`--check` fails when the committed files are stale; a unit test runs it). QA review of the fragments is still needed before AC8 numbers are quoted.
- **Held-out set.** `holdout_attacks.jsonl` and `holdout_benign.jsonl` (40 each, hand-written, not generated, never used to build or tune a detector). They exist because a detector written with the main set in hand looks better on it than it is.
- **Runner.** `forge injection run --detector <d> --set main|holdout|all [--min-block-rate x] [--max-fp-rate y] [--json]` prints the block rate (attacks blocked) and the false-positive rate (benign blocked), by language and category, with samples of misses and false positives; the two options make it a CI gate.
- **Detectors** are plugins: `none` (the floor), `heuristic` (normalised-text rules in English and Italian, with base64, rot13, leetspeak, spaced-letter and invisible-character handling) and `command:<program>` (text on stdin, `block` or `allow` on stdout), so the Phase 2 guardrail models (E2.11, ADR-013) can be scored without code changes.
- **Measured (2026-10-19)**: `none` blocks 0 % and flags 0 %. `heuristic` blocks **94.3 %** of the main set with **2.5 %** false positives (all in security discussion, where quoting an attack phrase is indistinguishable by rules), but only **2.5 % of the held-out attacks** (1 of 40), with no false positives there. The rules were written with the main set's techniques in view, so the 94 % is an upper bound for rule matching, and the held-out number is the honest one: a keyword baseline does not generalise. The Phase 2 detectors must be judged on held-out and independent data, and QA should grow the held-out set toward the size of the main one.
- The agent-with-canary mode named in the first draft (send each attack to a test agent holding a secret and count leaks) is **not built**: it needs a model and belongs with the guardrails (E2.11) and evaluation datasets (E3.2).

## 9. Threat-model delta

| Threat | Control |
| --- | --- |
| SSRF through `http_get` | Allowlist per agent, resolve then check every address, private ranges refused, redirects re-checked, caps on size, time and content type |
| Indirect prompt injection through tool or document text | Results delimited as data and declared non-instructions; no tool can change the agent's own configuration; injection guardrails on tool results arrive with E2.11; the E1.21 dataset measures the baseline |
| Cross-project or cross-user run access | RLS on all tables; `run.read.own` filtered in the query; SSE checks the run before streaming; Redis stream keys include the run id, never the user's choice |
| Runaway cost and loops | Per-run limits (steps, tokens, cost, time) with platform ceilings; gateway quotas still apply to every call |
| Tool replay after a crash | `tool_call_log` idempotency key per tool call |
| Metrics leak | `/metrics` on an internal port only; labels never contain user, prompt or document content |
| Secrets or content in telemetry | Spans and logs carry ids, counts and names only; content in spans is off by default |

## 10. Choices to confirm with the PO

1. **Agent prompt = system template + examples**; the prompt's user template is ignored, because the chat message is the user turn.
2. **Conversations** keep only final answers as memory for the next turn; tool traces are visible in the run view but not re-sent to the model.
3. **Default limits**: 8 steps, 50,000 tokens, 120 s, 1.00 USD per run.
4. **`http_get` is off until the agent lists allowed hosts**, and private addresses are refused unless the deployment flag `FORGE_AGENT_ALLOW_PRIVATE_HOSTS` is on (needed for the lab).
5. **`usecase.run`** is the permission to chat with published agents; Builders can also chat with drafts.
6. **Injection dataset** is generated from reviewed templates; QA review of the content is still needed before AC8 numbers are quoted.
7. **Langfuse** is an optional Compose profile (`make obs/langfuse`), validated with `docker compose config` but not run end to end in Phase 1.
8. **The injection main set is generated** and the heuristic baseline was written with it in view; its held-out result (2.5 %) is the number to remember.
