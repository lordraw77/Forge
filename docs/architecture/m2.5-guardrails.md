# M2.5 Guardrails – design (slice a)

_Roles: Architect, Engineer, QA. Stories: [phase-2.md](../requirements/phase-2.md) E2.11. ADRs: 005, 013. Date: 2026-10-20._

## 1. Where it sits
The check runs inside `GatewayService.chat` (ADR-005), so every caller is covered — API keys, agents, use case steps, the Planner — with no per-caller code. Order: resolve → quota reserve → **input guard** → cache → call → **output guard** → record.

- Input: `user` and `tool` messages (string or text parts). Masked text replaces the message before the cache key is computed, so cached answers never depend on raw PII.
- Output: the answer's `choices[].message.content`. If the project has output rules and the call is streamed, the call runs whole and is replayed as a stream.
- A blocked call releases its quota reservation and is recorded in `llm_call` (input: `rejected`; output: `error`, tokens counted because the provider was paid).

## 2. Engine (`guardrails/engine.py`)
Pure functions, no I/O: `evaluate(text, stage, rules, models)` → `Verdict(text, action, findings, unavailable)`. Rules are applied in order on the text left by earlier masking; the strictest action wins (`block` > `escalate` > `mask`/`rewrite` > `log`). Model-backed checks come through the `models` map, which stays empty until a `guard` endpoint adapter exists (ADR-013).

## 3. Storage
Migration `0017`: `guardrail_policy` (one row per project, rules as JSONB) and `guardrail_event` (forced RLS both). Policies are cached 5 s per process.

## 4. API
`GET|PUT /projects/{id}/guardrails/policy`, `POST …/test` (dry run), `GET …/events`. Permission `project.manage`.

## 5. Choices to confirm with the PO
1. **The policy is optional.** A new project checks nothing until a PA saves rules, and the policy can be switched off; no default policy is seeded (PO: the policy must not be mandatory).
2. **Mask/rewrite on a check with nothing to cut blocks** (an injection cannot be "masked").
3. **Streaming with output rules is buffered**, so first-token latency equals total latency for those projects.
4. **Output blocks answer 502**, since the fault is the model's, not the request's.
5. **PII has two engines**: regex plus validators (Luhn, IBAN, codice fiscale) and Presidio + spaCy for names, places and organisations (§8).
6. **Phone numbers need an international prefix** (`+39…` or `0039…`) to limit false positives.
7. **The event log keeps labels, never text**; there is no retention job yet.
8. Dashboards of interventions belong to M2.6.

## 6. Not yet built
`tool_args` on use case tool nodes is covered by code but not by an integration test; `escalate` into the approval flow (today it blocks); test with the Phase 1 injection dataset through the policy.

## 7. UI (added the same day)
The policy screen is the *Governance* menu entry (`/governance`, Project Admins): enable switch, rules (check, stages, action, fail mode, parameters as JSON with an example per check), a dry run on sample text against the rules on screen, and the intervention log. The page states that guardrails are optional: no saved rules, or a disabled policy, means no call is checked. Parameters are a JSON box rather than per-check forms (to confirm with the PO).

## 8. Names, places, organisations (Presidio)
- Entities `PERSON`, `LOCATION`, `ORGANIZATION` in a `pii` rule (`params.entities`; never part of the default list) use Presidio with spaCy `en_core_web_sm` and `it_core_news_sm` (about 13 MB each). Presidio and spaCy are the `pii` extra, installed in every image; models live in `FORGE_MODELS_DIR/spacy`.
- Embedded images bake the models in (`forge models fetch --spacy`); `-slim` images download them on the first use (through the proxy), in a worker thread. A failed load is retried after 5 minutes.
- **Language**: the text is analysed in the language its common words suggest (Italian or English; a tie runs both). A model reading the wrong language invents entities (an Italian city tagged as an organisation), so running both always was rejected. `params.languages` limits the choice.
- The analysis is CPU-bound and runs in a thread, so the event loop and other calls stay free.
- **Fail-closed default widened**: a rule that cannot run (no Presidio, no models, no guard endpoint) blocks if it changes or stops text (`mask`, `rewrite`, `block`, `escalate`); only `log` rules pass. Without this, a `mask` rule on names would let unmasked names reach the cloud model whenever the models were missing. The policy screen lists `ner` as unavailable in that case.

### Choices to confirm with the PO (Presidio)
9. **Small models, modest accuracy.** `*_sm` models miss some names and tag some companies as places (tested: "Acme" read as a place). Larger models (`lg`, about 400 MB) are an image-size trade-off; Presidio runs only on explicit entities, so the cost is paid only by projects that ask for names.
10. **Licence**: `it_core_news_sm` is CC BY-SA 4.0 (the English one is MIT). It is downloaded data, not linked code, but legal should confirm it can be shipped inside the image.
11. **Names are masked, not pseudonymised**: every name becomes `[PERSON]`, so the model cannot tell two people apart in one prompt.
12. **Two languages only** (Italian, English), like the UI.

## 9. Guard models (toxicity, model-based injection)
- A `toxicity` rule, or an `injection` rule with `params.model`, asks a registry model of type `guard` (name or alias, enabled for the project). `params.threshold` (default 0.5) applies to score answers; `params.categories` limits which categories count. The heuristic runs first for `injection`; the guard is asked only if it found nothing.
- **Chat shape only** (OpenAI-compatible, ADR-013 first shape). Answers understood: Llama Guard (`safe` / `unsafe` + categories), NVIDIA content safety (`User Safety: unsafe` lines, the format NIM really returns, or the same keys as JSON), Prompt Guard (a probability, e.g. `0.9996`). All three were checked live against Groq Prompt Guard 2 and NIM Nemotron content safety. Anything else counts as "could not run".
- The call goes to the provider directly, not through `chat`, so a guard call is never guarded; it is retried and falls back along the alias like any call, and recorded in `llm_call` with endpoint `guard` (cost and tokens visible).
- It runs in a worker thread (the engine is synchronous) and hands the network call back to the event loop. Every guarded text costs one guard call per rule per stage: the latency of a guard rule is the guard model's.
- Saving a policy checks that each named model exists, is enabled and is a `guard` model (422 otherwise). A guard that is down fails closed for `block` rules and open with `fail_mode: open`.
- AC8: `forge injection run --detector 'guard:<model>@https://<base url>'` (key in `FORGE_GUARD_API_KEY`) scores a guard model on the Phase 1 dataset, waiting out 429 limits.

### Choices to confirm with the PO (guard)
13. **No default guard model.** The PA names one per rule; a rule without one is reported unavailable. The seed's `guard` alias (Prompt Guard, then content safety) mixes two jobs (injection and toxicity), so it was not made the default.
14. **A guard's answer is not cached**, so a retried or repeated text is classified again (cost).
15. **Generic classification endpoint**: built, see §14.

### AC8 measurement (2026-10-20, hand-written holdout, 40 attacks + 40 benign)
| Detector | Attacks blocked | EN | IT | False positives |
| --- | --- | --- | --- | --- |
| heuristic (Phase 1) | 2.5% | – | – | – |
| Groq Llama Prompt Guard 2 86M, threshold 0.5 | **30.0%** | 55% | **5%** | 2.5% |

**AC8 (≥ 90%) is not met by either detector alone, and no figure may be quoted as met.** Prompt Guard 2 is an English-focused 86M classifier: it misses almost every Italian attack and about half the English ones (prompt extraction, role play, tool misuse, multi-turn set-ups). The generated `main` set (440 + 440) was not run against it (about 45 minutes on the Groq free limit). Options for the PO: a multilingual or larger guard (Llama Guard 4, a hosted classifier), an LLM-judge rule through the gateway, or a lower threshold plus an Italian-aware heuristic; each needs a new run of this table. QA must also extend the holdout before any figure is quoted.

## 10. LLM as judge, and the `tool_args` stage
**Judge.** `params.judge: true` on a `toxicity` or `injection` rule makes an ordinary *chat* model the guard (no `guard`-type model needed). The text goes inside the instructions, between markers, in a single user message: with the text in a separate message a chat model answers it (refuses, or even complies) instead of classifying it. The answer must start with `SAFE`/`UNSAFE`; the free-text reason after it is ignored. Judge calls are accounted for like guard calls (endpoint `guard`). A rule naming a chat model without `judge: true` is refused at save (422).

**`tool_args`.** Before a tool runs, every string value of its arguments is checked on its own (so masking never breaks the JSON): agents' tool loop and `tool` nodes of use cases. A blocked call is not run and answers `guardrail_blocked` (the agent sees an error result it can react to; a tool node fails its run). The check happens before the human-approval step, so approvers see masked arguments, and again on edited arguments. Events carry `source = tool:<name>`. Tool *results* are checked as `input` of the next model call (role `tool`).

### Choices to confirm with the PO (judge, tool_args)
16. **A judge costs a normal model call per rule, per guarded text**, and adds its latency; it sees the user's text, so for PII it must be a model the project is allowed to send that text to.
17. **Judge instructions are fixed in code** (injection, toxicity), not editable per project.
18. **Masking tool arguments changes what the tool receives** (`[EMAIL]` instead of the address); the agent is not told.

## 11. Bundles
`guardrail_policy` is a configuration item of the bundle (export option, needs `project.manage`; no schema bump, old bundles keep importing). It carries `enabled` and the rules; guard models are named, never ids. Import **replaces** the project's policy (as `gateway_config` replaces limits), after the same validation as saving: a rule naming a guard or judge model the target project lacks makes the item an error and the current policy stays. A dry run validates without saving. The export dialog has a *Guardrail policy* box.

## 12. Grounding
A `grounding` rule (output stage only) asks a chat model (`params.model`, always as judge) whether every claim of the answer is supported by the call's **context**: the content of its `tool` messages, which is where RAG results and other tool outputs reach the model (capped at 30,000 characters, after input masking). A call with no tool messages has nothing to ground an answer in, so the check does not apply and the judge is not called. `UNSAFE` means "not supported". Calls with several choices check each choice. Saving needs a model and the output stage (422 otherwise); without a model the policy lists `grounding` as unavailable.

### Choices to confirm with the PO (grounding)
19. **Context = tool results only.** Passages put in the system or user message by an application (not through a tool) are not seen as context, so such calls are not checked. The agent runtime's RAG tools do arrive as tool messages.
20. **Same cost model as a judge**: one extra model call per grounded answer; with long passages that is a long prompt.
21. **Strictness is the judge's**, fixed in the instructions; no score threshold. It has been exercised against the mock only, not measured on real answers with a real model.

## 13. Per-agent rules
An agent version carries `guardrails`: a list of rules in the same format as the project policy (up to 20, validated when the version is saved). They are **added after the project's rules for every model call and tool call of that agent** (also when the agent runs inside a use case), never instead of them: an agent can be stricter than its project, never looser, and it needs no project policy to have its own. They are part of the version, so they are pinned, versioned, copied with the agent and travel in bundles. The agent editor has a JSON box for them.

### Choices to confirm with the PO (per-agent)
22. **Additive only.** An agent cannot switch off or relax a project rule; a project with a lenient policy cannot be made strict by an agent for others.
23. **No guard-model check at save**: a rule naming a guard or judge model the project lacks is accepted and then follows its fail mode at run time (closed by default), instead of refusing the version (the model may be enabled later).
24. **Events do not say which rules were the agent's**: agent rules are numbered after the project's (`rule_index` ≥ number of project rules).
25. **JSON box, not a form**, as on the project policy screen.

## 14. Classification endpoints (ADR-013, second shape)
A `guard` model whose `params` hold `"shape": "classify"` is a plain HTTP classifier, not a chat model (a Prompt Guard or toxicity model behind text-embeddings-inference, or any service with that contract). Forge POSTs `{"text": …, "inputs": …}` (the same text under both names: `inputs` is what TEI expects) to the provider's `base_url` + `params.path` (default `/classify`), with the provider's API key as a bearer token and its custom headers. Two answers are read: `{"labels": [{"name", "score"}]}` and TEI's `[[{"label", "score"}]]`. The text is unsafe when a label **not** in the safe list scores at least `threshold` (rule `params.threshold`, default 0.5); the flagged labels are the categories. The safe list defaults to `safe, benign, neutral, not_toxic, non-toxic, nontoxic, ok, clean, none` and can be set per model with `params.safe_labels`.
- Used by `toxicity` and `injection` rules exactly like a chat guard model (fallback along aliases, `llm_call` rows with endpoint `guard` and no tokens, fail modes). It cannot be used with `judge: true` or `grounding`, which need instructions (the call fails and the rule follows its fail mode).
- *Test Connection* on such a model posts `ping` to the endpoint and shows the labels it returned.
- Plain-HTTP and credential rules are the provider's: the endpoint is the provider's `base_url`, the outbound proxy applies (`httpx` reads the proxy environment).

### Choices to confirm with the PO (classification endpoint)
26. **The request body is fixed** (`text` and `inputs`); a service that rejects unknown fields needs an adapter or a field setting (not built).
27. **The safe-label list is a convention** (names above); a classifier with other safe labels needs `safe_labels`, otherwise its "safe" label could count as a finding.
28. **Configured in the model's JSON parameters**: the Models page has no dedicated fields for `shape`, `path` and `safe_labels` yet.
