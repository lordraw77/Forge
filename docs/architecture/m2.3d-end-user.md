# M2.3d End-user catalog, sessions and runs – design

_Roles: Architect, Engineer, UX, QA. Stories: [phase-2.md](../requirements/phase-2.md) E2.9. ADRs: 010, 015. Date: 2026-10-20._

Scope: the end-user Use Cases Catalog (cards, search, filters, favorites, recent), the use case page with its generated form, sessions and run history, the run page with progress over SSE, outputs (Markdown, JSON, DOCX, XLSX, PDF) with downloads, the run API (sync, SSE, async with webhook), file inputs, the requirements attachment deferred from M2.3c, and API-key visibility by the creator's Role Name.

## 1. Pages (`/catalog`)

| Page | Route | What it does |
| --- | --- | --- |
| Catalog | `/catalog` | Card grid of the published use cases the user's Role Name may run; search (name, description), category and tag filters; views *All*, *Favorites*, *Recent* (the last 12 use cases the user ran); star to favorite |
| Use case | `/catalog/:id` | Description, tags, output type, the input form generated from the **published version** (text, long text, number, choice, file upload), *Run*, and the user's own runs of this use case with *Open* and *Run again* |
| Run | `/catalog/runs/:runId` | Status, steps/tokens/cost/time, a timeline of the steps as they start and end, the result, downloads, *Stop*, *Run again*, the other runs of the session |
| Runs | `/catalog/runs` | The user's run history (operators, builders and admins: the whole project) with a status filter and *Run again* |

End users never see agents, prompts, tools or graphs. The home page buttons now open the catalog and Build Your Own.

## 2. What an end user sees of a run

`GET /use-case-runs/{id}` redacts for callers without `run.read`: no graph, no limits, steps reduced to `node_id` and status/timing (no input, output, reference, agent run id or error text), outputs reduced to `result` (and `file_error`). With `run.read` (Operators, Builders, Admins) the response is as before. API keys follow the same rule through their scopes. Run history, `export` and file downloads use the same visibility: own runs, or all runs with `run.read`.

## 3. Sessions

A session is created by the first published run started from the catalog (title = first line of the first text input, else the use case name). `RunStartIn.session_id` adds a run to an existing session (404 for sessions of other users or other use cases). Each run stays pinned to the version live when it started. Sessions are private to their author, even for admins; test runs have no session. `GET /use-case-sessions` and `/use-case-sessions/{id}` list them.

**Re-run** (`POST /use-case-runs/{id}/rerun`) starts a new run with the same inputs in the same session on the version **live now** (a test run is re-run as a test run, builders only). Input files are re-used by id.

## 4. Progress: SSE

`GET /use-case-runs/{id}/events` streams `run` (status and totals, when they change), `step` (one per step start and end) and `done` (the final run). The server polls the database once a second and keeps no cursor: **every connection starts from the full state**, so a refreshed page picks a running run up and `Last-Event-ID` is not needed. The stream ends at `done`; it is bounded to 3 hours. The same generator serves `delivery: "stream"` of the run API.

## 5. Run API (`POST /use-cases/{id}/runs`)

`delivery`:

- `async` (default): 202 with the run; poll it, or give a `webhook_url`.
- `sync`: waits up to `timeout_s` (1 to 300, default 60); 200 with the finished run, or 202 with the run as it is when the time passes.
- `stream`: 200 `text/event-stream` with the events above, starting with `run`.

**Webhook.** `webhook_url` is checked when the run is started with the rules of the tool egress policy (the project's allowed hosts, public addresses unless `FORGE_TOOLS_ALLOW_PRIVATE_HOSTS`): 422 `invalid_webhook` otherwise. When the run ends a Temporal activity POSTs `{event, run_id, use_case_id, use_case_name, version, status, error_code, cost, finished_at}`; a non-2xx answer or a network error is retried (4 attempts, 2 s then ×3). The result is on the run: `webhook_status` `pending` / `delivered` / `failed` and `webhook_error`. The body never carries the output: the receiver fetches it with its own API key, so a spoofed call can leak nothing. A dead webhook never changes the run.

**API keys** see the use cases of the Role Name of the user who created the key (key permissions are the scopes ∩ the creator's permissions, as before); the catalog, the run and the files follow the same 404 rule.

## 6. Files

`use_case_file` (kind `input`, `requirements` or `output`) with the bytes in object storage under `projects/<project>/usecases/files/<id>`.

- **Input files.** A form field of type `file` takes the id returned by `POST /use-case-files` (multipart, up to 100 MB). Forge reads **text, Markdown, CSV, JSON, PDF, DOCX and XLSX**; the text is extracted once at upload and stored beside the file (`<key>.txt`), so an unreadable file is refused at the form (422 `unsupported_file`) and a run never re-parses it. At start the field must name a file the caller uploaded (422 otherwise); the worker puts the **extracted text** (at most 200,000 characters) into the variable, so templates use `{doc}` like any text input.
- **Requirements attachment** (deferred from M2.3c): `POST/GET/DELETE /use-cases/{id}/requirements-file`, one per use case (a new one replaces the old), builders only; the Planner receives an excerpt of the text (20,000 characters). The requirements page has an optional file input.
- **Output files.** For output type DOCX, XLSX or PDF the worker renders the final output when the run ends and stores it with the run **before** the status becomes `succeeded`, so a reader that sees the status finds the file. A rendering failure leaves the run `succeeded` and says so in `outputs.file_error`. Markdown and JSON are produced on demand by `GET /use-case-runs/{id}/export?format=markdown|json`.
- **Downloads** (`GET /use-case-files/{id}/content`) check the visibility of the run (outputs) or the uploader (inputs, requirements); everything is sent as `attachment` with `nosniff`, and uploaded files always as `application/octet-stream`.

`render.py` (pure functions) parses Markdown into headings, paragraphs, bullet and numbered lists, code and pipe tables and writes them with python-docx, reportlab and openpyxl (all permissive licences; the gate passes). XLSX of a JSON array of objects becomes a table, an object becomes field/value rows, Markdown tables become one sheet each plus an *Output* sheet.

## 7. Data

Migration `0015`: `use_case_session`, `use_case_favorite`, `use_case_file` (forced RLS) and `use_case_run.session_id`, `webhook_url`, `webhook_status`, `webhook_error`. The workflow gained the activity `uc_notify_run`; `uc_finish_run` has a 120 s timeout because it may render a file.

## 8. Choices to confirm with the PO

1. **The result is shown as plain text.** Markdown is not rendered (no renderer in the bundle yet); downloads give the real formatting. A safe Markdown view can be added if wanted.
2. **End users see step names and status only**, never what an agent said in the middle of the run; the final result is the only content. Builders have the test page for that.
3. **Progress is not a token stream** for end users: the page updates when steps start and end. Live tokens exist on the builder test page.
4. **Webhook body without the output and without a signature**, hosts limited by the project's egress allowlist (the same list as Tools).
5. **File inputs become text.** No OCR, no spreadsheets as tables: an XLSX reaches the graph as `sheet | cells` lines. Images are refused.
6. **DOCX, XLSX and PDF come from a built-in renderer**, without templates or company branding.
7. **Re-run uses the version live now**, not the version the original run used.
8. **Sessions are private**, also for admins; admins see the runs (US-2.9.2 #3) but not the session grouping of others.
9. **Favorites and recent are per user and project**; *Recent* shows the last 12 use cases run.
10. **Builders can read the input files of runs** (they have `run.read`), since the run inputs are visible to them anyway.

## 9. Tests

Unit: `catalog-util.spec.ts` (filters, helpers; 6), `render` exercised through the integration tests. Integration `test_usecase_end_user.py` (10, including the dead webhook retried to `failed`): redaction for end users vs builders; sessions, re-run and privacy; DOCX output stored and downloaded with visibility rules, export; XLSX and PDF; favorites and recent; sync and stream delivery and the events endpoint; webhook refused/delivered/failed; file inputs (unreadable, empty, foreign and invalid ids, text reaching the agent, octet-stream serving) and the requirements attachment; API key visibility following the creator's Role Name. E2E: `catalog.spec.ts` (cards, search, favorites, form, run page, failure, run again, history; no model is reachable so the run fails).
