# M2.4 Human in the loop – design

_Roles: Architect, Engineer, UX, QA. Stories: [phase-2.md](../requirements/phase-2.md) E2.10. ADRs: 004, 010. Date: 2026-10-20._

Scope: runs that wait for a person. Three triggers (the `human_approval` node, `hitl: true` on a node, a `tool` node whose tool `requires_approval`), decisions from the UI, the API or a one-time email link, notifications by email and webhook, the Approvals inbox, the public review page and the builder pieces (node drawer, Planner).

## 1. How a run waits

```
engine ──approve(call)──▶ workflow ──activity uc_wait_approval──▶ worker
                                         │ creates `approval` + a step, run → waiting_approval,
                                         │ notifies (email, webhook), then polls the row (2 s)
 person ──POST /approvals/{id}/decision──▶ API writes the decision (row = source of truth)
                                         │ worker sees it, closes the step, run → running
engine ◀── {decision, edited, comment} ──┘
```

- **The wait is an activity, not a signal** (this refines ADR-004 item 6). The activity heartbeats and polls the approval row, so a lost signal is impossible, a killed worker is simply retried and picks the wait up again (the approval row and its step are keyed by run and step key, so nothing is created twice), and the API needs no Temporal client for decisions. Cost: up to 2 s between decision and resume, and one idle activity per waiting approval.
- **The run time limit counts work, not waiting.** The workflow stops the clock while any approval is pending (`timeout_s` limits the work; the approval has its own limit). A test proves a run with `timeout_s: 5` survives 8 s of waiting.
- States: `running` ⇄ `waiting_approval` (back to `running` when the last pending approval of the run is decided); `finish` also accepts `waiting_approval`, so a run cancelled while waiting ends properly and its pending approvals become `cancelled`.

## 2. The three triggers (engine)

| Trigger | When | Content | Approve | Reject |
| --- | --- | --- | --- | --- |
| `human_approval` node | at the node | `input` rendered; `instructions`; output variable = approved text | output = the (edited) text | run fails `approval_rejected` with the feedback |
| `hitl: true` on agent / tool / llm | after the node produced its output | that output | output = the (edited) text | **agent**: re-run with the previous answer and the feedback appended to its task, up to 3 times (steps `a`, `a~r1`, `a~r2`…), then `approval_rejected`; **tool / llm**: fails (repeating them would not change anything) |
| `tool` node, tool `requires_approval` | before the call: the activity answers `needs_approval` with the planned arguments | tool and arguments (JSON) | the call runs with the (edited) arguments, same step | run fails `approval_rejected`; the tool is never called |

Node fields: `instructions` (template), `assignees` (Role Names), `timeout_hours` (1–720; default `FORGE_APPROVAL_DEFAULT_HOURS`, 72). Validation checks them and variables used in `input`/`instructions`. Approval steps are not counted in `max_steps`; their step key is `<step>~approval` (`:approval` in the end-user view).

## 3. Who can decide

`approval.decide` (Project Admin, Builder, Operator by default). With `assignees`, only those Role Names and Project Admins; anyone else gets 404, also from the list. Edits are bounded (64 KB) and typed: text for reviews, a JSON object for tool arguments. Decisions are transactional (`SELECT … FOR UPDATE`): a second decision, one after expiry or after cancellation answers 409. Every decision is audited. The starter of a run, who usually cannot decide, sees only the status; the review content is not part of the run view.

## 4. Notifications and one-time links

- On creation the worker finds the members allowed to decide (`TenancyService.approvers`) and, if `FORGE_SMTP_HOST` is set, emails each one the use case, the step, the review URL and a **personal one-time link** `…/approve/<token>`. Without SMTP nothing is sent; the inbox works anyway. Failures to send are logged, never raised.
- Token `fap_<project>_<256-bit random>`: only its SHA-256 is stored, bound to approval and user, valid until the approval expires, and **consumed by the first decision of the approval by any means** (UI, API, other person's link).
- The link opens a public page (`/approve/:token`). Viewing (`GET /api/v1/approval-links/{token}`) never decides, so mail scanners are harmless; deciding is a `POST`. The decider recorded is the user the link was sent to, who must still have `approval.decide` in the project. Bad, used or expired tokens answer 404 with no detail.
- If the run has a `webhook_url`, it also receives `use_case_run.approval_requested` (run, approval, use case, node, review URL; no content, no token).

## 5. API

`GET /projects/{id}/approvals?pending=true`, `GET …/approvals/{id}`, `POST …/approvals/{id}/decision {decision, edited?, comment}`; public `GET|POST /api/v1/approval-links/{token}[/decision]`. API keys can decide with the scope `approval.decide` (key permissions = scopes ∩ creator's). Migration `0016`: `approval`, `approval_token` (forced RLS).

## 6. UI

Approvals page (`/approvals`, in the menu; also linked from the catalog for approvers): pending items, optional decided ones, a review dialog with the content in Monaco, *Approve*, *Approve with changes* (when the text differs) and *Reject* (comment required). The test run panel links to it while a run waits. The canvas has an *Approval* node and, for agent/tool/prompt nodes, the *Human in the loop* box with instructions, assignees and hours. The Planner knows the new fields.

## 7. Choices to confirm with the PO

1. **Approvals pause graph and supervisor runs, not an agent's own tool loop.** A `requires_approval` tool called by an agent (chat or inside a use case step) is still refused with `approval_not_available`; pausing mid-loop needs the agent runtime to checkpoint at the call. Backlog.
2. **Waiting is a polling activity, not a signal** (ADR-004 said signal). Same durability; simpler and cannot lose a decision.
3. **Reject re-runs only agents.** For a `human_approval` node, a tool or a prompt, rejection fails the run with the feedback (3 re-runs maximum for agents).
4. **Default wait is 72 hours** (node setting up to 720), then the run fails with `approval_timeout`.
5. **Email only through deployment SMTP settings** (`FORGE_SMTP_*`); no GUI form and no per-project SMTP yet. One personal link per approver; the same page serves approve and reject.
6. **The webhook announces the approval but carries no decision link** (a webhook has no user to bind a token to). Receivers use the review URL or the API with a key.
7. **The end user who started a run cannot see what is being reviewed**, only "waiting for approval".
8. **Approver lists are not limited to people**: a project with no member holding `approval.decide` cannot resume; the run times out after the wait limit.

## 8. Tests

Unit (`test_graph_engine.py`, +6): approval node with edit, rejection, `hitl` re-run with feedback and its limit, tool arguments edited / never called when rejected, field validation. Integration `test_approvals.py` (11, real Temporal, SMTP sink, mock HTTP): pause/resume with edit and API checks (422/403/404/409), rejection, `hitl` re-run, tool approval with edited arguments and rejection, assignees, cancelling a waiting run, expiry, the run time limit not consuming the wait, email + webhook + one-time link (viewing does not decide, single use, dead after another decision), tenant isolation. E2E `approvals.spec.ts`: empty inbox and a dead public link without a session.
